# 设备管理可靠性与界面复核 — 2026-10-06

本轮继续产品开发，范围为手机和桌面的「设置 → 设备与安全」。所有交互均连接隔离的真实 Hub，未操作用户生产设备授权、VPS 或 Bot 实例。界面延续现有暖砂配色，将日常设备管理放在配对教程之前。

## 已复现并修复

| 场景 | 修复前 | 当前行为 |
| --- | --- | --- |
| 撤销授权成功，随后 GET 列表失败 | 撤销被误报失败，仍显示可撤销 | 以写入回执更新授权状态；刷新失败单独提示 |
| 设备改名成功，随后 GET 失败 | 报重命名失败，旧名称可能继续显示 | 立即显示已确认的新名称，后台刷新不会回滚 |
| 改名未保存后关闭设置 | 手机和桌面均可直接丢稿 | 分类切换保留草稿，退出或主机管理入口要求明确放弃；继续编辑返回设备页 |
| 旧列表请求慢于新的写入回执 | 旧结果可覆盖已撤销/新名称 | 请求编号和生命周期检查阻止过期结果覆盖 |
| 初次列表读取失败 | 空白列表，缺少重试入口 | 加载、失败、离线分开显示，提供刷新入口且保留键盘焦点 |
| 改名保存中离开、重复点击、离线操作 | 改名未纳入全局保存状态；编辑框未遵守离线禁用 | 写入串行，保存期间保护退出，离线保留草稿并禁止提交；空白名称不提交 |
| 改名写入遭拒 | 两处重复错误，焦点可能跳出输入框 | 错误只在原行显示，焦点返回输入框；错误信息关联输入控件 |
| 服务端已写入，但回执丢失 | 只报告失败，列表保持旧状态 | 明确提示结果未确认，自动读取列表核对，不自动重复写入 |
| 切换语言 | 已存在的成功提示仍是旧语言 | 成功与设备操作错误在渲染时翻译；配对码、设备名称等用户内容保留原文 |

设备请求使用 20 秒超时。后台刷新不锁住返回或分类导航。撤销按钮消失后，操作结果成为键盘焦点落点。当前设备仍不显示撤销自身的入口。

首轮四个回归用例在修改前全部失败（撤销桌面/手机、改名、手机草稿）。最终浏览器回归覆盖真实写入、数据库读回、读取失败、响应乱序、丢失回执、离线、键盘焦点、两端设置层级、中英文与 320px 窄屏。

## Opus 5.5 xhigh 参与情况

使用本机 Claude CLI 的 `claude-opus-5-5 --effort xhigh` 做了两次有界审查，均关闭会话持久化；JSON 回执均为 `success` 且 `modelUsage` 为 `claude-opus-5-5`。第二次同时读取本轮手机截图。

- 首轮重点：写入和刷新混淆、旧响应覆盖、改名草稿、重试入口与焦点。
- 第二轮追加：重复报错、回执丢失后的主动核对。两项均已实现，并通过真实 Hub 的拒绝写入及「先提交到服务器，再丢弃回执」用例验证。
- 更正审查输入：首轮输入曾把新设备进入列表的时机描述错了。实际 `HubAuth.approve` 在批准时就插入设备记录，第二轮已明确纠正。没有采用基于错误前提的轮询等待方案。
- 截图中灰色按钮背景是现有 hover 样式；键盘 `focus-visible` 的描边仍保留。未凭单张截图将其当作确定 bug。

## 界面步骤

1. 打开设备与安全，已授权设备、当前设备标记与刷新入口优先显示。
