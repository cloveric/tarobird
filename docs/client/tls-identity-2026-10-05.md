## 与原计划的差距

原计划 §8.3 要求中转被冒用或证书被冒签时仍能拒绝连接；§12.14 还要求
VPS 出示另一张证书时客户端拒绝。现有 `verifyHub` 验证持久身份公钥和双方
随机数，能拒绝伪造签名，但签名没有绑定实际 TLS 对端。正常 TLS 直通情况下的
[公网抓包验收](relay-privacy-2026-10-05.md)仍然成立；它没有验证主动终止 TLS 的中转。

两个隔离实验确认缺口，未使用真实聊天、附件、账户或在线机群：

- Node：临时测试 CA 签发两张不同、同主机名有效的证书。所有连接保持 CA 与
  主机名检查，中转分别与客户端和真实 Hub 建立 TLS。中转原样转发真实 Hub
  签名及设备签名，随后读到短期令牌、把合成用户消息改写后提交，并凭该令牌
  独立读取会话目录，返回 200。
- Chromium：当前打包的真实 `HubConnection` 完成正常配对。通过浏览器测试
  拦截器模拟已进入 TLS 内部的中转，转发签名握手后，同样读到令牌并改写了
  Hub 最终保存的用户消息。此实验验证实际客户端逻辑，不充当 TLS 或原生验收。

## 本轮实现的范围

`GET /api/tls-identity?nonce=<32 字节随机数的 base64url>` 返回：协议版本、
固定消息类型、Hub 公钥、请求随机数、当前连接的本机叶证书 DER SHA-256，以及
Hub Ed25519 签名。签名使用独立的 `tarocub/tls-identity/v1` 域及明确的数组编码，
不能作为设备认证签名或短期访问令牌。

证书只来自服务端当前 `TLSSocket.getCertificate().raw`，包括实际 SNI 选择；
请求参数和转发头不能选择被签名的证书。明文 HTTP 返回 426，响应禁止缓存，
签名请求有独立的来源限速。该接口不建立设备会话、不访问用户内容。

共享验证器要求调用者提供**本端 TLS 栈实际观察到的叶证书哈希**。它核对可信
Hub 身份、此次随机数、证书哈希和签名。把响应里的哈希再传回验证器会失去保护，
禁止这样使用。普通网页 `fetch` 和 `WebSocket` 不能提供这个受信证据，故本轮
没有给浏览器添加一个虚假的“证书已校验”状态。

新增实际 TLS 测试覆盖正常连接、另一张受信证书透明代理、响应改写、旧随机数、
另一 Hub 身份、未经信任 CA、错误主机名、TLS 直通、SNI 不同证书、明文接口、
任意哈希注入和限速。即便代理转发的是有效 Hub 签名，校验器仍因实际证书不同
而拒绝；改写签名中的证书哈希则导致签名无效。

Opus 第二次针对实现的复核认为这个狭义证明成立，并提出了补充边界。
父代理收紧公钥／签名的 ASCII 格式，统一验证异常，加入认证／吊销／TLS 签名
跨用途拒绝、真实证书轮换和共享 TLS 私钥的对照测试。所谓“签名接口可能互相
冒用”经检查固定前缀和实测未复现，不能记成已确认漏洞。

Hub 的 TLS 私钥必须只在 Hub 上，不能与 VPS、CDN 或其他服务共享；持有相同
证书私钥的代理会通过证书绑定，此情况已有明确的对照测试。原生实现还必须
拒绝 TLS 1.2 重新协商、按主机和证书隔离 TLS 会话恢复、限制 pin 缓存时长，
在新连接池和证书变化时重新验证。当前按来源限速在中转后可能共享一个来源桶，
因此还有可用性边界，不能将限速测试称为完整抗拒绝服务能力。

## 完整修复还必须落实

1. 原生受控网络栈：Tauri/Rust、iOS URLSession、Android 原生 HTTP/WebSocket
   都必须在发送设备身份、令牌或用户内容前完成验证，并固定后续连接的证书。
   每条线路、连接池、TLS 会话恢复、重定向、证书轮换和并行文件请求都不能绕过。
   另开一次探测连接而继续使用未固定证书的 WebView 请求，仍有漏洞。
2. 首次配对：扫描可信主机二维码或独立核对指纹，绑定 Hub 身份与本设备公钥。
   仅从同一未受信连接读取 Hub 公钥属于首次使用信任；8 位批准码本身不能防止
   中转替换配对设备的公钥。需要单独复现并验证配对完整性修复。
3. 浏览器边界：如果 SPA 本身由被冒用的中转源提供，攻击者能直接替换应用代码。
   即便另加应用层加密也不能解决该代码来源问题。原计划的原生错证书拒绝要求
   保留，不以“应用层加密后代理只能看到密文”替代。独立可信来源的浏览器访问
   若继续覆盖该威胁，需要经过审查的认证加密传输，涵盖 WS、HTTP 和附件。
   **范围决定，2026-10-05**：原计划 §1 排除应用层端到端加密，用户现已明确
   “先不加密，以后再说”。因此本阶段不扩展该层加密；TLS、配对及原生证书
   固定继续落实。桌面端和手机 App 为产品重点，浏览器用于预览／调试；不再
   等待浏览器范围答复，也不以该决定声称浏览器已抵御上述攻击或删除已有能力。
4. 完整攻击回归：真机安装受控测试 CA；另一张有效证书必须在敏感请求前被拒绝。
   同时复测流式停止、双线路切换、120 MiB 续传、512 MiB 内存、撤销和配对，
   保留正常直通对照。不能仅凭本文新增的校验器测试关闭 §12.14。

实际 Opus 的报告建议把应用层认证加密与原生证书拒绝分开处理；它未审阅的
其他组件推测不计为已复现漏洞。报告中的 DNS/CAA、配对及原生实现建议尚未部署。
本轮不改用户 DNS、VPS、防火墙、已安装 App 或在线 Bot。
