## 已复现并修复

### 终态卡片不等于执行成功

Gateway 的卡片投递使用 `complete` 表示消息传输结束，Core 的 `nativeRun.phase`
才说明执行是完成、错误、部分完成或中断。旧工单只检查消息 envelope 的 `error`，
因此真实 Gateway/Core 返回错误卡片并 ACK 输入后，工单被误判为 `needs_review`。

现在聚合前台 run 的真实终态：`error` 进入失败分类；`partial/stopped/interrupted`
进入 `blocked`，保留结果，并明确提醒幕僚长核对产物、向主人确认，不能自动重派。
子任务 `scopedRun` 的失败不会机械覆盖父任务已经完成的结果；仍活动的子任务
继续阻止过早结算。主人暂停/取消的原有停止证据要求不变。

Opus 另复现：父任务已处理子任务失败并完成后，恰逢主人暂停，旧停止分支仍把
子任务失败当作未完成，重新排队。暂停前、暂停后两条路径现以父任务完成为准；
只有子任务完成、没有父任务完成的情况仍不能作为停止后的完成证据。

实际 Gateway、Core、Hub 隔离集成复现覆盖 quota、auth 和普通错误；模型 bridge
是替身，没有调用真实模型。不能把这称为已安装版或真实引擎验收。

### 较早任务完成误清较新引擎限制

两个同引擎工单并发，较新工单先报告额度不足，较早工单随后完成时，旧实现会
无条件删除引擎健康状态。正常结算、暂停前已完成、暂停后确认完成三条路径均复现。

成功现在只清除 `updated_at < attempt.startedAt` 的健康记录；同毫秒保守保留。
主人显式清除仍可无条件执行；失败后新启动的强制尝试成功仍可证明恢复。
这沿用既有持久化时间戳，不新增 schema。系统墙钟回拨仍可能破坏时间先后判断，
完整解决需要持久化执行/健康代次；本次没有扩展到该协议。排队输入虽在限制后真正
执行，但记录的开始时间较早时可能保留限制，owner 清除及冷却到期路径保持可用。

### 操作结果未知后的新暂停/继续

Opus 在真实浏览器与隔离 Hub 复现：暂停已生效但响应丢失，继续后再次点击暂停，
客户端复用第一次暂停的编号。Host 正确回放旧回执，新的暂停却没有执行。

保留结果未知操作的原编号，直到操作成功，或操作结束后新发出的读取显示其状态
已经生效。之后的新暂停/继续生成新编号；任务提问、备注、更新时间等进度变化
不会让编号失效，旧读取也不能充当操作已生效的证据。不会自动重发操作。

复审否决了最初仅比较 `updatedAt` 的候选：同一未知操作期间，worker 发起审批使
更新时间变化，新候选会误换编号。新增负向浏览器用例在该候选失败、原版通过；
最终修复必须同时通过旧缺陷和这条防回归用例。此处仍为浏览器 transport/丢包替身
测试，不代表原生 pinned transport 或组件重建后的重试验收。
多设备间在两次读取之间完成“暂停→继续”，本设备又恰好丢失暂停回执时，仍可能
在首次重试读回旧操作回执；仅凭当前状态无法证明中间发生过这次往返。本轮没有
新增跨设备动作代次协议，也未声称消除了这类跨设备时序风险。

## DeepSeek 逐条裁定

原始报告将 D1–D10 都标为“确认发现”。复核区分可复现的行为与违反现有约定的
缺陷；不能将 10 项直接当成 10 个 bug。Opus 已逐条复核并冻结客户端文件，
没有合入阻断项；报告为 `opus/opus-deepseek-adjudication.md`。下表为最终整合裁定。

| 项目 | 裁定与处理 |
| --- | --- |
| D1 终态错误卡片误判成功 | 真缺陷，已修；补经过实际 Gateway/Core/Hub 的失败集成测试，模型 bridge 为替身。 |
| D2 部分完成、停止、中断误判成功 | 与 D1 同一聚合缺陷；进入卡住状态，保留已做工作，避免自动重做。 |
| D3 旧成功清除新限制 | 真缺陷，已修；覆盖普通结算及暂停前后，同毫秒保守保留。 |
| D4 Bot 能将工单标为 done | 是既有自然语言验收接口，不是新权限漏洞。主人在对话中验收后 Bot 需要能登记完成；验收约束由指引表达，非服务器二次审批。保留接口并写明边界。 |
| D5 取消中 paused=true | 是禁止再次派单的中间态保护；界面以 stopRequested 显示“正在取消”，结算后收敛。不能为了标志名好看去掉保护。 |
| D6 归档会话导致永久无法重派 | 归档阻止重派属预期，“永久”不成立。独立隔离 Hub 验证归档后拒绝、主人恢复后同一会话可重新派单；补恢复步骤，不自动取消主人归档。 |
| D7 update 丢响应后重试报错 | update 本来没有 requestId 回执；可用 show 核对当前结果。补 Bot 指引和文档，避免把已取消误当失败并重派；不扩展协议。 |
| D8 最后复检落败仍准备 worker/目录 | 并发窗口内的可复用资源开销。启动留在事务外避免阻塞共享数据库；最终事务仍阻止重复输入及超额占槽。不在失败补偿中删除可能被其他派单复用的 worker。 |
| D9 人工 ACK、零回复仍待验收 | 探针可构造，但未证明真实 Gateway 丢结果；无输出/清理历史不必然等于执行失败。保留“没有文字回复”与待验收，不自动重做。ACK 也不能普遍等同成功，D1 正是反例。 |
| D10 删除幕僚长后无法读账本 | Bot 控制随删除退役，历史及文件保留，不能为读取重新开放已删除 Bot 的控制。另确认提示误称 show 返回“完整结果”：实际只留 4,000 字符摘要，已修正文案并说明从工单打开完整执行会话。 |

H1 陈旧等待卡、H2 缺 reply_to、H3 文本分类误判均无真实触发证据，不按假设修改。
H4 将回送描述为主人指令不准确：消息带 Bot 来源，Gateway 将其标为委派输入，
不能用作主人授权。该边界不等于宣称已消除所有模型提示注入风险。

也复核了 Opus 的表述：D9 的 Gateway ACK 仅说明 handler 收到成功回执，不能证明
模型任务成功，Core 捕获错误并输出错误卡后也可能返回该回执；本轮 D1 集成测试
已验证这一点。H1/H2 应写“未复现”，不能由已读路径推成所有路径绝不发生。
不采纳自动另建会话绕过主人归档的可选建议。Bot 验收增加消息来源硬限制属于
新的授权约定，本轮保持既有自然语言验收行为，没有自动扩大或收紧授权。

Opus 建议按子任务/父任务更新时间判断“已修复”的方案未采纳：时间先后不能证明
父任务看过并处理子任务错误；本次保留父任务权威终态和活动子任务占槽规则。
真实 Gateway 的迟到后台子任务场景尚未验收，不用合成时间戳替代结论。
