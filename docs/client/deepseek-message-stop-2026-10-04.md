# DeepSeek：按消息停止与排队撤回

范围：TaroCub 管理的原生 DeepSeek Harness 0.2.0-rc.2，独立临时主机，桌面浏览器与 390 × 844 手机浏览器配对。没有修改生产 Bot、全局 DSH 配置或安装包。

## 修复的行为

旧实现对普通消息停止和超时使用 `session.cancel`。该原生接口取消当前 Agent，但保留 inbox；当普通消息排在自主目标后面时，会误停目标并让被撤回的普通消息随后执行。

现在每条普通输入都有独立 `requestId`。发送请求一旦提交，停止会保留其接收回执的等待，避免先停止、后入队；不会重发原输入。主机现有私有继承管道新增 `cancel-prompt`，在原生进程内连续核验和操作：

- 尚在 inbox：只删除 `source.rpcId` 匹配的条目，并退休该输入的上传回执。
- 已进入本条消息的轮次：核验原生来源，排除先进入的其他用户或目标来源，取消该轮次并保留其他排队消息。若有已启用的原生目标，明确拒绝单独停止，避免原生 goal driver 连带暂停目标。
- 已结束或被后续任务替代：提示停止到达前已结束，不取消后来的任务，也不把这种情况写成“已中断”。此前未同步的最终内容仍需查看原生主机记录。
- 不能确认身份或主机不支持：返回明确的未确认状态，不退回整个会话取消。

原生 `agent/inbox/claimed` 通知覆盖取出输入后、异步提示词组装完成前的窗口；记录本轮来源顺序，后台工具通知不冒充用户，合并到其他任务的消息不能取消那个任务。检查与操作之间没有异步等待。可选文件回执清理失败也不会否定已经提交的撤回。

App 输出另外按确切 `requestId` 归属。未见到当前输入的来源时，旧消息的迟到正文、终态和空轮次都不能完成或中断新消息；后台复查只能在这条输入已确认进入之后归属。

无法取得停止确认时，App / 飞书及 Telegram 都显示“尚未确认停止”，提醒检查主机、避免重复发送。不会把用户的 abort 信号本身当成已经停止的证据。接收请求超时后会保留占用并短暂重查晚到的输入；原生明确拒绝与网络结果未知分别处理。请求或管道失联导致的未确认不等于消息已被撤回；本次未实现跨进程故障下的永久撤回凭据。

## 验收

`client/e2e/live-goal.spec.ts` 的 `queued-stop` 流程使用真实原生 CLI 和实际模型输出：

1. 桌面创建 Bot 并启动自主目标，等待故事正文真正出现。
2. 手机发一条普通消息，观察其精确编号进入原生 inbox。
3. 手机停止普通消息，取得 `removed` 回执；两端显示中断，目标正文仍继续增长，没有 `goal.clear` 或 `session.cancel`。
4. 停止目标后，确认被撤回的编号从未成为原生 `user/message`。
5. 开始新的普通长回复，手机停止，取得 `cancelled` 和该原生轮次的 `aborted` 终态。
6. 同一原生会话继续回复；两端刷新后仍看到结果。

Chromium、WebKit 均已跑通上述流程。证据、截图、审查回执和最终校验结果在 机器可读验收记录（本地材料：`evidence/deepseek-message-stop-2026-10-04.json`）。本地管道回执耗时只代表本机操作，不代表公网或手机端到端速度。

另一个独立的真实原生测试先运行普通长回复，再启用目标。停止普通消息得到 `goal-active`，目标仍 active，原生历史没有 aborted 轮次；显式清除目标后，同一个消息编号可以正常取消。这个测试没有浏览器 UI，不作为手机验收。

实际 Opus 5.5 xhigh 只读审查（本地材料：`evidence/deepseek-message-stop-opus55-2026-10-04.md`）指出目标驱动器的取消副作用、来源归属、取出到记录之间的窗口、过早完成回执、晚到接收和可选服务清理问题。上述实现与专项测试据此补齐；审查针对变化中的源码，未声称 Opus 又审批了最终版本。

针对性测试还覆盖延迟接收、撤回期间新消息占用保护、其他排队条目、已有目标、取出但未记录的输入、过期轮次、工具授权撤销、未确认回执、不同语言错误与禁止自动重发。模拟竞争测试与真实浏览器流程分别记录，不能互相替代。

## 限制

实体手机、系统键盘、后台生命周期和公网断网组合尚未验收。DeepSeek 目标本身与普通输入并存时的目标停止、严格目标用量归属及并行引导仍是独立验收项。这次没有修改 UI 样式、重新打包 r10、替换已安装 App 或部署服务。
