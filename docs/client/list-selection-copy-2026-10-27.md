# Selected list copying — 2026-10-27

## Behavior

Rendered list markers are generated by the browser, not ordinary text nodes.
The desktop selected-text action previously used `Selection.toString()` and
could omit these markers. Native clipboard behavior also varies by engine.

`message-selection-clipboard.ts` now projects a selection containing complete
list-item prose into two clipboard formats without changing the displayed DOM:

- Plain text carries original ordered-list numbers (including a non-one start,
  counter reset and reversed counters), bullet markers and nested indentation.
  Selecting items 3–4 copies `3. …` and `4. …`, not 1–2.
- Only complete own prose earns an item's marker. A partial leading/trailing
  item retains its selected fragment; complete intervening items keep numbers.
  A partial-only selection delegates entirely to native copy.
- Paragraphs, code whitespace, table cells and rows remain readable. Task-list
  check state is written as `[x]` / `[ ]`. Fully selected formulas copy their
  source notation once, avoiding KaTeX's parallel accessibility/visual trees;
  partially selected formulas retain native copy rather than adding unselected
  formula content.
- HTML contains semantic lists, counter values, emphasis and permitted links.
  App IDs, event handlers, images, controls and layout classes are not exported.
  Unsupported rich Clipboard API writes fall back to plain text; if that also
  fails, the existing App error path reports failure.

Keyboard/native Copy and the desktop “copy selected text” menu use the same
projection. The menu snapshots the payload before selection changes. An App
copy listener only handles a list selection within one message surface or
message viewport; it does not monitor selection changes or intercept shortcuts.
Counter values are calculated once per list per copy, avoiding quadratic scans
on long selections. No live DOM markers or stored content are mutated.

Whole-message copy continues to read original Markdown. Phone long-press
“Select text” already exposes the original numbered text in a readonly field;
that path and input-field editing remain native. The ordinary conversation and
ADHD panes share the same message content and clipboard handler. Headless CLI,
Host protocol, database, engine output and clipboard behavior outside message
surfaces are unchanged.

## Validation boundary

`client/e2e/message-selection.spec.ts` exercises real keyboard copy and paste
into the App composer, semantic HTML paste into a browser rich-text editor,
context-menu copying, partial/nested selections, table/formula/task content,
multiple messages, original counters, clipboard fallback and the actual phone
selection-sheet entry. Existing selection, toolbar-exclusion, portal and native
context-menu regressions remain included.

Final candidate: **18 Chromium + 18 WebKit checks passed**. Client production
build (including translations and TypeScript) and standalone Host/CLI build
passed. Evidence is retained in the local `list-selection-copy-20261027/`
directory. Initial test-fixture failures were corrected to await the real
asynchronous clipboard write and use the phone's actual selection-sheet entry;
the final complete runs used those corrected paths.

Browser rich-text paste checks the supplied HTML contract; it does not establish
that every Word/Pages version preserves exactly the same formatting. Real Mac
WebView and iPhone/Android selection handles were not newly tested. This is a
source change; it does not release or replace the installed App.
