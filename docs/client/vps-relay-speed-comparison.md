# VPS 中转与飞书速度对照 — 2026-10-02

结论：当前公网中转的文字消息传输足够快；大文件明显慢于本机对飞书文件接口的
实测。SSH 对照也复现了 Mac 向这台 VPS 上传较慢，提示首要瓶颈在该方向的网络
路径，不能把全部差距归因于中转代码，也不能据此宣称已定位运营商或云侧限速。

## 方法与范围

- 同一台 Mac、同一网络，连续时段测量；主测试在北京时间 15:48–15:53 完成，
  随后执行 SSH 对照。没有配置环境变量 HTTP/HTTPS/ALL_PROXY。
- TaroCub：两个独立配对的协议客户端，经公网 VPS 的 8443/7443 端口连接本机
  隔离 Hub；没有 Tailscale 或 SSH 转发。HTTPS 复用连接，TLS 校验开启。
- 飞书：通过 `lark-cli 1.0.97` 的 bot 身份调用 IM 文件上传和下载接口。
  计时包括 CLI 启动、认证和接口开销；未往任何会话发送消息。
- 文件采用完全相同的随机字节：1 MiB、8 MiB，各方向各两次；每次完整下载均
  验证字节数与 SHA-256。相同内容重复上传可能受服务端缓存影响，两边均保留
  两次原始结果。样本数有限，不是长期吞吐量承诺。
- 这是协议/API 测量，不含原生界面渲染、手机蜂窝网络、模型思考、语音识别。
  飞书聊天收发尚未实测，不能比较两款 App 的完整聊天体验。

## 消息延迟

计时为发送消息到另一协议客户端收到 `message.created`，使用同一进程的单调
时钟。双向交替发送，不靠轮询估计到达时间；所有 100 条公网测试消息收到确认
并到达另一端。文件负载期间每组 30 条消息覆盖传输的前一段时间。

| 场景 | 样本 | 中位数 | P95 | 最大值 |
| --- | ---: | ---: | ---: | ---: |
| 公网中转，空闲 | 40 | 28.2 ms | 48.6 ms | 120.9 ms |
| 公网中转，同时上传 8 MiB | 30 | 29.0 ms | 113.8 ms | 189.1 ms |
| 公网中转，同时下载 8 MiB | 30 | 29.0 ms | 147.4 ms | 160.5 ms |
| 本机 loopback 基线 | 30 | 0.83 ms | 1.82 ms | 2.71 ms |

空闲时发送确认中位数为 28.2 ms、P95 为 48.6 ms。两次新 WebSocket 建连、
身份认证及初始同步分别约 219 ms、290 ms。Loopback 不代表真实局域网速度。

## 文件对照

下表为每项两次的平均总耗时；上传包括创建记录、传输和完成确认。速度按文件
字节数除以平均耗时计算，单位 MB/s 为十进制；8 MiB = 8,388,608 字节。

| 项目 | TaroCub 公网中转 | 飞书 IM 文件 API | 本次耗时比 |
| --- | ---: | ---: | ---: |
| 1 MiB 上传 | 1.33 s | 1.22 s | 波动大，不作倍数结论 |
| 1 MiB 下载 | 1.68 s | 0.90 s | 约 1.9 倍 |
| 8 MiB 上传 | 14.48 s，0.58 MB/s | 2.98 s，2.81 MB/s | 飞书约快 4.85 倍 |
| 8 MiB 下载 | 14.28 s，0.59 MB/s | 1.19 s，7.03 MB/s | 飞书约快 11.96 倍 |

8 MiB 单次上传为 14.32/14.63 秒，下载为 14.31/14.24 秒；同时聊天时上传
14.64 秒、下载 14.50 秒。此前两个客户端并行下载 120 MiB 分别花费 423.71 秒、
453.09 秒，各约 0.30/0.28 MB/s。此前 120 MiB 上传包含主动中断、VPS 重启和
恢复，不作为纯吞吐量对照。

## SSH 对照与下一步

绕开应用中转，用 SSH 直接传输相同 8 MiB 随机文件，两次结果：

| 方向 | 第一次 | 第二次 |
| --- | ---: | ---: |
| Mac → VPS | 13.11 s，0.640 MB/s | 13.29 s，0.631 MB/s |
| VPS → Mac | 1.16 s，7.24 MB/s | 0.69 s，12.18 MB/s |

SSH 计时包含新连接与认证，单程路径也不同于应用往返路径，因此只用来诊断方向，
不冒充优化后的 App 速度。Mac → VPS 在两种实现下都慢，且和中转吞吐量接近。
当前 TLS 透传模式把文件保存在 Mac，每次下载都再次经过 Mac → VPS 慢链路。

后续优先项：

1. 在已授权的方案中实现有期限的 VPS 附件缓存，让多设备下载复用一次上传。
   缓存仍需独立的加密、授权、容量和清理设计，本次没有部署缓存。
2. 对 Mac → VPS 做分时段/备用 VPS 对照，定位线路、区域和云侧带宽约束。
   暂无证据证明换协议或提高 CPU 就能解决。
3. 继续完成下载断点续传。它主要减少失败后的重复传输，不等于提高链路带宽。
4. 在用户指定的测试会话、真实桌面和手机上测飞书与 App 的消息送达/渲染时间，
   再单独比较相同模型、同一提示词的首字时间。
