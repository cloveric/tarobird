## Confirmed findings and changes

### P2: a failed App projection could strand the final reply or a committed input

`HubServer` used to log `broadcast_failed` without recovering connected Apps.
When the last `message.updated` projection failed, the database already contained
the complete answer but the App stayed at the streaming revision. Heartbeats
continued successfully, and no later event necessarily existed to expose a gap.
The same failure on `message.created` skipped `dispatchPending`, because Bot
dispatch was chained to successful App publication. A synthetic worker received
no input even after three maintenance sweeps; reconnecting the worker recovered
it. This is a previously existing recovery gap, not a claim that October 26
streaming optimization introduced it or that its production frequency is known.

The committed input now uses the same durable, per-Bot dispatch path independently
of App broadcast completion. A projection failure terminates only original
recipients with access to the affected conversation that are still behind, or
are still synchronizing that conversation. Their existing reconnect path recovers
from the persisted cursor or a replacement snapshot. No raw unprojected payload
is sent; per-frame authentication and visibility checks are preserved.

A second review caught an ahead-cursor boundary: a client can arrive with cursor
100 when the Host is at 1 and be waiting to ACK its replacement snapshot. The old
hello cursor is not proof it received a new event at 2. Synchronizing clients are
therefore handled before comparing cursors. Clients that joined later or already
completed a covering snapshot remain connected. Workers are never stopped by
this App recovery, and retrying the same `clientMsgId` does not dispatch twice.

Changed: `src/hub/server.ts`, `tests/hub-server.test.ts`, `client/e2e/stream.spec.ts`.
CLI impact: shared Host reliability improves identically for a desktop-owned or
standalone Host; no additional CLI command, protocol capability or schema.

### P3: another ADHD pane's auto-scroll hid the hovered message toolbar

The delegated pointer toolbar listened to every captured document scroll. A
reply in pane B auto-following to its bottom cleared the toolbar under a
stationary pointer in pane A. Opus reproduced the module behavior in Chromium
and WebKit; root reproduced it with real Hub updates and the full ADHD UI.

Scroll now clears ownership only when the scrolling element contains the active
message, or the document itself scrolls. Mouse leave, touch, keyboard focus,
dialog focus, blur and disconnected rows retain their prior handling. A streamed
reply in another pane leaves quote/copy controls usable; scrolling the owning
pane still retires the old toolbar. No dimensions, colours or accessible names
change. CLI-not-applicable: client pointer presentation only.

Changed: `client/src/message-action-hover.ts`, `client/e2e/adhd-search.spec.ts`.

### P3: settled disabled-label contrast and a timing-dependent test

Opus found white-violet/light disabled primary labels settling at **4.4739:1**.
The existing folder Save test requires 4.5, but could pass by sampling a colour
halfway through the theme transition. Root independently reproduced the failure
at both phone and desktop widths after awaiting the button's real animations.
Inactive controls are exempt from WCAG 1.4.3; this is a small legibility and
repository-test-contract defect, not a claim of a mandatory conformance failure.

Only white-violet disabled primary/card labels now use the existing secondary
foreground (`--grey`), giving **7.18:1** on its light disabled surface. Other
palettes, active buttons, global muted text and geometry are unchanged. The
existing regression awaits transitions instead of accepting intermediate values.
Changed: `client/src/porcelain-details.css`,
`client/e2e/conversation-folders.spec.ts`. CLI-not-applicable: presentation only.

### Test-only: WebKit hit-target coordinate precision

The independent baseline reported the 320px list-options button as
`43.99998474121094px` against an exact `>= 44` assertion. Its intended hit target
is unchanged. `client/e2e/sidebar-layout.spec.ts` now allows only `0.001px` of
coordinate rounding at that boundary; no production CSS or size was changed.

## Boundaries

Opus also noted that entering conversation details/history search hides the side
panel, releases the owned window expansion, and reacquires it on returning. This
is consistent with reserving extra native width only while the panel is visible;
the side handle/draft survive. The existing manual-resize and space fallback
rules still apply. It is documented rather than classified as a reproduced
defect or changed into a new persistent-window-size preference during this audit.

The completed physical Mac side-window acceptance belongs to the preceding
`c2884daa` change; this audit did not reinstall it. Browser phone widths and
WebKit are not physical iPhone/ColorOS acceptance. No new native Windows,
multi-monitor/fractional-DPI, real relay/Tailscale, production-scale disk
compaction, push end-to-end or five live-model performance claim is made.

An already-admitted eight-digit pairing code retains its pre-existing wall-clock
approval deadline; turning the system clock backwards can lengthen that approval
window. The invitation itself uses monotonic expiry and cannot admit new devices
after expiry, and owner approval is still required. Recorded as an existing
boundary rather than broadening this audit into an auth-format migration.

No release, installation, production migration, `hub compact`, forced stop or
backup-policy change is part of this audit. The Android wrapper's unrelated
line-ending normalization is excluded from the commit.
