# Qwen3-ASR 手机 M4A 解码修复

## 问题与原因

标准 ASR 环境升级依赖后，手机的 Opus 音轨封装在 MP4/M4A 中，旧调用
`normalize_audios(path)` 依赖的文件解码后端不能读取该容器，导致转写返回 500。
这与模型是否支持中文或服务是否在线无关。librosa 1.0
[移除了 audioread 回退](https://librosa.org/blog/posts/1.0/)，原来可通过回退解码的文件因此暴露问题。
此前迁移验收没有覆盖这种真实手机录音，是测试缺口。

## 实现和边界

- `integrations/qwen3-asr/server.py` 增加 `decode_to_wav`，用现有 FFmpeg
  直接解码至 stdout，再将小端 s16le 转为单声道、16 kHz、float32 PCM。
  没有新增 Python 依赖，也不创建临时音频文件。
- 使用参数数组、`-nostdin`、120 秒超时、明确的第一条音轨，以及本地文件/管道协议限制。
  时间和字节输出上限共同约束解码；实际音频超限时拒绝整个输入，不发送截断内容给模型。
  解码失败、无音轨、空输出、非法 PCM 和超时以脱敏 `ValueError` 交给原 HTTP 400 路径。
- 原 `validate_audio`、300 秒上限、分片、短片段跳过、推理缓存回收、请求锁和看门狗未改动。
  AST 对比确认除 `transcribe_chunked` 的导入及解码调用外，原有 16 个函数/类保持不变。
- CLI 的 `transcribe.py` 导入同一 `transcribe_chunked`，修复同时覆盖 HTTP 和 CLI；
  不需要新 CLI 命令或不同的引擎适配实现。CLI 冷启动的真实模型推理本轮未单独运行。

`activeRequests=0`、失败计数为 0，看门狗仍为显式开启且内存监测可用。

本轮未发布新的 App/CLI 安装包，已签名 App 和既有 macOS/Windows 构建缓存没有原地修改。
现有 1.0.95 App 使用已修复的本机标准服务即可受益，但该版本内置的安装源仍是旧脚本。
后续正常发版必须重新生成独立 Host 包，再由桌面打包器复制该包，不能沿用旧暂存资源。
自动故障修复的 `--restart` 只重启现有脚本，不覆盖它；从旧包重新安装则仍有回退风险。
回滚需再次取得空闲独占锁，恢复对应备份并重启、复核健康和实际转写，禁止在请求处理中强制替换。
