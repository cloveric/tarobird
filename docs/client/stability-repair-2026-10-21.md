# 客户端稳定性修订：缓存恢复、附件生命周期与历史读取

日期：2026-10-21。基线：`1f26ba2660f8f5159c5082b7573ed3cb2724ed49`。

本轮针对初审已复现的问题修订，保留既有消息顺序、队列去重、身份验证及授权撤销机制。不是以代码行数判断稳定性，也不是全系统无缺陷的声明。

## 行为变化

### 本地缓存关闭后的恢复

`ClientCache.isClosed` 是缓存是否已退役的权威状态。IndexedDB 升级导致的 blocking 和异常终止均关闭该句柄；不按任意 `UnknownError` 猜测永久失效。

连接在启动、握手准备、接收、恢复和发送入口检查此状态。已退役的连接停止定时重试，提示关闭其他窗口并重新打开应用，不删除身份、聊天、草稿或待发队列，也不将本地存储失败累计成健康线路故障。若在连接池启动阶段失败，原有池可用新句柄重试，但不会复活旧句柄。身份与撤销检查照常执行。

发送入口仅对需要持久化排队的请求做缓存检查；若缓存刚关闭而已验证的 socket 尚在线，`turn.stop` 等直接控制帧仍可发送。连接一旦进入终止态，则按原有离线规则处理，不重新打开旧句柄。

缓存准备与本地密钥签名耗时不再惩罚线路；等待网络/主机、伪造主机挑战、协议错误仍沿用线路冷却。配额不足仍保留既有暂停与人工重试机制。

### 被动附件加载

`PassiveAttachments` 按连接、附件 ID 共用一次在途加载，每个连接最多 3 个网络下载；缓存命中不排在网络下载后面。预览中的待加载图片优先于普通缩略图。

每个阅读组件持有一个消费者租约。最后一个消费者离开后给予 750 ms 宽限期，处理快速切换、线路切换和 React 重新挂载；仍无人使用才中止。排队但已无人使用的条目不启动网络请求。其他仍打开的图片或音频不受影响。

消费者离开造成的中止不显示错误；连接终止时仍挂载的阅读器显示失败/重试，不停在“加载中”。完成或中止后移除池内条目；不由池长期保留 Blob。

主动保存、带独立取消信号的下载和文件流仍使用各自生命周期。原有校验、断点续传和持久化预算保留：被取消的大下载可能留下受原有容量与期限限制的分片，供后续续传。并发预算不能等同于所有平台总内存上限；图片解码与多个主机还需原生测量。

### 聊天与目录刷新

普通聊天的消息与待发列表复用 ADHD 已有的会话级修订号。其他会话更新不再重复读取当前会话整段历史；全局快照、ACK、当前会话变化和显式刷新仍有效。侧边栏继续订阅全局状态。

主机目录观察器一次只执行一组读取，运行期间的任意多次刷新合并为下一次读取。切换主机或注册实例后，旧读取不会发布到新视图；失败保留上一份有效数据。未改动 App 中其他目录读取、网络授权轮询频率或消息接收顺序。

### 图片慢速滑动

基线在超过 1 秒的明确横向拖动后不切图。移动手势改用方向与距离判定，保留缩放、双指、取消和纵向滚动规则；双击的时间限制仍保留。触摸测试包含明确超过 1.1 秒的拖动。

- 缓存及连接：`client/src/storage.ts`、`connection.ts`、`connection-verification.ts`。
- 附件：`passive-attachments.ts`、`use-attachment.ts`、`ImagePreview.tsx`、`LinkPreview.tsx`。

CLI 不适用：修改的是浏览器/原生 WebView 的本地缓存与阅读器资源生命周期，Host API、数据库结构、授权与 headless CLI 行为没有新增或变更。不新增另一套主机实现，不改模型适配器。

## Opus 审阅发现及处理

实际使用 Opus 5.5、effort xhigh，方案审阅、实现审阅、收尾复审与收尾增量确认均已完成。各阶段原始记录保存在私有任务证据目录，不将私有运行记录提交公开仓库。

实现审阅发现两处确证缺陷并修正：

1. 连接关闭与消费者退出都使用 AbortError，会让仍挂载的图片一直加载。改为携带关闭原因，补单测及真实 Hub 组件回归。
2. 部分本地签名错误仍导致线路冷却。改为签名阶段统一本地归因，并验证主机签名不匹配仍被拒绝和冷却。

收尾复审另指出缓存检查误挡无需入队的停止控制帧，已将检查限定到持久化发送并补回归；历史测量计数改在读取调用时累加，避免漏掉尚未完成的读取。测量中的输入耗时是自动化 `fill` 往返加两帧，不称为真实手机输入延迟。

另修启动阶段向调用方返回的缓存错误提示；保持网络发送异常归因。Opus 独立执行客户端单测 200 项通过，收尾增量再执行连接启动和附件单测 24 项通过，并检查 TypeScript 与翻译。Opus 未执行浏览器或原生验收；这些不与 Codex 结果合并。收尾确认以上发现已处理，未遗留双方意见分歧。

双方同意不凭推测修改授权轮询、丢弃接收帧或任意设置通知去重 TTL。以下是后续测量/改进候选，尚不是已确认并修复的缺陷：接收队列峰值与同步吞吐、每 4 秒网络同步轮询、App 自身未合并的目录读取、附件/头像读取的事务模式，以及多主机与大图下的原生内存。同步用例的 20 秒等待上限不是性能承诺，仍需独立吞吐基准。

## 额外发现与后续修复：超长正文渲染

现有 `performance.spec.ts` 的 5,000 段流式回答 + 10 表格/公式测试未达到原门槛：本轮三次帧间隔 P95 约 217–283 ms、最长任务约 790–831 ms。未修改的基线同样复现（采样开启时 P95 266.6 ms、最长任务 831 ms）；采样结果只用于定位，不当作严格 A/B。Opus 只读复核浏览器 timeline，确认主要长任务位于原生 Layerize 和定稿布局重算。

最初改变段落隔离、分块包裹和内容可见性等隔离实验仍未达标，并存在主题子选择器、滚动锚点风险，因此没有混入第一笔缓存/附件修复提交。后续独立定位到流式前缀交付饥饿、逐段隔离及定稿新增节点集中绘制，完成有生命周期保护的渐进绘制和完整主题选择器迁移。

最终原有 5,000 段性能用例三次串行通过，帧间隔 P95 均约 16.8 ms，均未记录到 ≥50 ms 的长任务；内容与门槛不变。原始及中间失败日志保留。具体修订、补测和 Opus 复审见 [长回复专项记录](streaming-markdown-stability-2026-10-21.md)，原生设备及 WebKit 验证边界仍保留。

## 已知验证边界

- WebKit 在创建空白页面时超时，未进入 TaroBot；脱离项目的独立空白页探针和默认临时目录重试同样失败。系统日志包含 WebKit 网络进程 XPC/TCC 连接失败。记录为环境阻塞，不算产品测试通过。
- Chromium 的手机视口与原生桥替身不能替代 Android/iOS 真机，也不能证明 macOS App Nap、Windows WebView2 或原生取消时延。
- JS 堆、对象 URL 与监听器检查不包含解码后的图片表面、所有 Worker 和系统进程内存；测量需如实注明范围。
