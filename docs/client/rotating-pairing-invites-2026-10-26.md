# 限时设备邀请与严格首次配对（2026-10-26）

## 目标与边界

原来的连接二维码包含主机身份和线路，不是可直接读取聊天的登录凭证；新设备仍需所有者确认八位码。但二维码长期不变，公开 `/api/pair` 不要求持有二维码，旧链接可以长期用于提交申请。本次同时收紧主机准入和 App/CLI 入口，不只是改变二维码图案。

采用用户明确选择的严格兼容方式：**首次连接必须使用新版 App、支持邀请的新版 Host 和有效限时邀请**。不为旧 App、局域网、环回地址、中转或配置开关保留公开绕过。已经配对的设备继续使用原设备密钥重连，不重新扫码。原生桌面及本机 CLI 控制器保留原来受本地操作系统/控制管道保护的登记流程；它们不是网络 `/api/pair` 的例外。

本次仅提交源码、测试与文档，不安装、不重启主机、不发版，也不操作生产数据库。将来升级 Host 和新设备 App 后才会实际启用。

## 用户流程

1. 已授权的所有者在「设备与网络 → 添加设备」、主机局域网/Tailscale 设置，或 CLI `tarobot pair` 获取限时连接码。
2. 每份邀请有效 **5 分钟**，只准入 **一个具体设备的一次申请**。打开入口签发一次，显示剩余时间；过期隐藏二维码，由用户重新生成，不在后台无限续期。
3. 新设备扫码或粘贴完整连接信息，确认名称后提交。Host 返回该设备的八位配对码。
4. 所有者核对并明确批准后，新设备才能通过身份认证并读写聊天。扫到二维码不等于获得授权。

「重新生成连接码」替换该入口先前未使用的邀请，不启动监听器、不重启主机、不改组网线路。改变网络配置使用独立的「网络变了？重新准备线路」。向导从二维码页翻到输入八位码的下一页，不撤销邀请；真正关闭整个向导才尽力撤销。离线关闭时撤销可能无法送达，最迟仍在原五分钟期限到期。

临时断线不签发新码，不延长期限。恢复后检查原邀请状态：已被使用或主机重启导致记录丢失时隐藏旧码。不同主机的迟到回执不会显示为当前主机二维码。

已经准入的八位码有独立的五分钟批准期限。刷新、撤销二维码或邀请本身过期，不会取消已准入的请求；该请求仍需明确批准。

## 协议与实现

| 入口 | 合约 |
| --- | --- |
| 能力协商 | `pairing-invites.v1`；公开 `/health` 返回 `pairingInvites: 1` |
| 所有者 `POST /api/devices/invites` | `{requestId, replaces?}` → `{id, invite, expiresAt, serverTime}` |
| 所有者 `GET /api/devices/invites` | 仅当前签发设备自己的邀请状态和已绑定设备信息，不返回 token |
| 所有者 `POST /api/devices/invites/revoke` | `{id}`，关闭当前设备签发的邀请 |
| 首次 `POST /api/pair` | 原 `deviceId/name/platform/publicKey` 加 `invite/requestId`；仍返回 `{code, expiresAt, hubPublicKey}` |

`invite` 和请求编号分别使用独立的 32 字节随机数，base64url 无填充编码。邀请 ID 是另外的 16 字节随机数，不能用作配对凭证。链接保持 `tarocub://pair?data=…` 的 v1 数据格式，邀请放在单独的 `&invite=…`。拒绝重复或未知参数，不接受向批准码注入邀请。旧客户端可解析地址用于已配对主机的线路修复，但不能完成首次登记。

核心文件：`src/client-protocol/pairing-invites.ts`、`src/hub/pairing-invites.ts`、`src/hub/auth.ts`、`src/hub/server.ts`；App 三个生成入口共用 `ConnectionInviteCode.tsx`，新设备由 `Pairing.tsx` 和 `storage.ts` 管理申请恢复；CLI 的 `pair`、`devices invites`、`devices revoke-invite` 使用同一管理 API。

Host 只在有界内存中保存邀请 token 的哈希，重启使邀请失效。双时钟覆盖休眠和系统时间倒退。单邀请串行处理准入，数据库事务提交后才绑定完整设备字段和请求编号；事务失败不消耗邀请。不同设备/公钥/名称/请求编号不能重用已绑定邀请。所有者被撤权或换密钥后，其邀请不能继续准入。

每个签发设备最多 8 份、整个 Host 最多 64 份仍能准入或持有未批准请求的邀请。批准后释放名额；失效/关闭/已批准记录作为短暂回执最多保留 64 条、60 秒，正在处理的记录计数但不被提前删除。单邀请另有准入尝试、重复回执及并发队列上限。无效 token 不创建 pending 行、审计事件或新的来源地址限速桶。已有的八位码审批限速继续生效。

## 恢复、升级和秘密存储

新设备先持久化身份和本次请求，再发 HTTP，避免丢回执后换密钥或重复登记。首次结果未知时暂存原邀请和请求编号，不能假定已被使用；取得八位码或明确收到 invalid/expired/used 拒绝后，移除原邀请，只保留请求编号。批准并认证上线后清理 pending 状态。邀请不保存到长期线路、Host 注册表副本或运行日志。

同一准入请求可凭完整设备字段及高熵请求编号取回同一八位码，不需再次持有原 token。这条路径只能恢复已存在的请求，不能注册新设备。缓存写入比较原 code/requestId，迟到回执不能复活已批准申请或覆盖另一份申请。

Host 在准入后重启、且新设备尚未收到回执时，内存恢复信息会消失，数据库待确认申请仍保留。可能需要等旧申请最多五分钟后过期再扫描新邀请；界面解释等待，不换身份、不删除他人请求。不确定的回执不提供随意覆盖原申请的操作。地址也变了时，先用现有「无法连接？更新主机地址」核对线路；重新扫码不暗中替换已信任线路。

首次严格升级在主机身份冲突与占用检查通过之后、公开监听之前，一次性清除旧机制产生的未批准 pending 请求并写入标记。已批准设备、主机身份、聊天、附件和备份策略不变；schema 仍为 22。以后重启不重复清理按邀请准入的申请。

CLI 需要运行中的新版 Host 及已登记控制器（`tarobot enroll`）。CLI 已更新而服务仍旧时，应在任务结束后运行 `tarobot restart`。`pair --json`、`--out` 含有效邀请，不应进入公开日志；`--out` 保持仅当前用户可读写。每次运行 `pair` 创建新邀请，超过容量用列表/撤销命令处理，不扩大上限。

## 独立审查与修复

root 实现 App/CLI/服务入口；Claude Opus 5.5 xhigh 实现邀请状态机并独立审查集成，再交叉复核；另一测试代理迁移回归 fixture。确认并修复：

- 已批准记录退出容量计数但仍免于清理，可能累积并超出列表 schema；连续 300 次批准探针从 300 条/列表校验失败变为 64 条/成功。
- 所有者先点「已扫码，输入配对码」会卸载并撤销邀请，而新设备尚未提交；步骤间保持挂载，关闭向导才清理。
- 断线重连重建邀请，离线撤销失败导致名额累积；保留 scope 和上次线路，重连检查原邀请。
- HTTP 结果未知时删除新设备私钥，旧回执覆盖新申请；先保存身份、比较后写入，并保留结果待确认状态。
- 没拿到八位码却提示批准“现有配对码”、失败 token 留存、异主机回执串用等恢复边界。
