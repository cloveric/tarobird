# Android 多主机通知注册与自审

2026-10-04。源码把 Android UnifiedPush 从单个全局实例改为每台主机独立注册。
每台运行主机仍使用自己的 Hub、配对身份与推送回执；手机上的分发器应用共用。
这是程序与本地回归里程碑，尚不是 Android 真机后台送达验收。

## 行为与恢复

- 逻辑实例由完整 Hub 公钥指纹和设备 ID 共同生成；两台 Hub 恰好使用相同设备 ID
  也不会碰撞。每次移除后重新注册使用新的 connector ID，旧注册的迟到回调失效。
- 新注册先保持未确认状态，取得 Hub PUT 回执后才确认原生记录。失败的新注册会
  回滚；即使回滚持久化失败，未确认的注册也不能被自动维护写回 Hub。通知总开关
  保留用户已选分发器，改用 FCM 使用单独的显式按钮。
- 注册、刷新、删除按主机串行执行；一台主机网络慢不会堵住另一台。全局清理单独
  等待所有既有操作，后续操作也不能越过它。
- 注册等待超时只约束原生端点获取；已经开始的 HTTP 写入必须完成或失败后才释放
  队列，防止后发 DELETE 被排队 PUT 覆盖。通知开关的写入也留在这个顺序中；
  定时器结束后的原生回调不能再发 PUT。
- 删除先持久记录“正在清理”，拒绝端点回调与刷新，再取得 Hub 删除回执，随后注销
  connector 并删除记录。网络或持久化失败保留清理状态，设置提供“继续完成清理”。
- 切换 FCM 在写入 Hub 前先持久停止旧 UnifiedPush 的回调与刷新；进程此时退出，
  重新连接也不会把旧端点写回去。成功后只清除此主机旧注册，本地清理失败可重试，
  不误删新的 FCM 注册。远端删除尚未完成时禁止直接切换，先完成清理。移除一台
  主机不会删除其他主机共用的 FCM token。
- 原来的单主机记录只能由原始 `tarocub-v1` 缓存认领，保留既有 connector ID 和加密
  元数据。启动导入之后立即在本地认领，不等待 Hub 在线；自动升级后尚未打开 App
  时，旧注册仍可显示不带主机身份的通知，多主机下不猜测其导航目标。旧版原生接口
  不支持这个契约时明确拒绝，要求更新 Android 客户端。
- Plugin 与 Service 使用同一存储实例和锁；提交失败不发送成功事件。移除中的记录
  不接受消息；推送数据的主机身份必须与注册所属主机一致，缺省时采用注册的身份。
- 每台已连接主机都维护自己的端点，不要求先打开它的聊天界面。分发器更换需先处理
  使用旧分发器的其他主机，不能静默替换。仅移除离线主机仍沿用明确的本地清理说明。

## SDK 契约

检查了实际使用的 connector 3.3.5 源码：多个 connector 实例共用保存的分发器。
`unregister(instance)` 清理指定实例的本地注册和密钥，并发送注销广播；最后一个实例
移除后也清除保存的分发器。它不是等待第三方分发器返回删除回执的同步接口。
因此本文的删除确认区分 Hub HTTP 回执、本机持久状态与第三方服务实际送达。
[UnifiedPush 官方 API](https://unifiedpush.org/kdoc/connector/org.unifiedpush.android.connector/-unified-push/)
说明与项目内使用的 3.3.5 源码需一起核对，在线文档可能对应更新版本。

## 验证与边界

生产 Java 注册状态机使用真实 `org.json`、JUnit 4 和 JDK 21 执行，覆盖主机隔离、
代际拒收、提交失败恢复、旧数据迁移、分发器约束和非法端点。不是只跑空壳示例测试。
客户端定向测试验证原生接口契约与队列顺序；设置页面使用受控的 native/HTTP 替身，
覆盖失败重试、分发器限制、端点刷新及 FCM 切换。它们不能作为 OS 推送回执。
正常 App 的多主机、设置、本地清理与返回行为同时回归。

实际调用 Opus 5.5、effort xhigh 做只读审查，禁用会话持久化和 MCP。
首轮读取的是正在修改的早期版，不能当作最终版本验收；随后对修复后版本再审。
原文、逐项处理、执行结果及范围见配套 evidence 记录。

当前验证：Java 状态机 8 项；Chromium/WebKit 各 35 项（其中 9 项为不依赖
浏览器的控制器测试，在两套配置中重复执行，不重复累计）；根检查 232 文件、
3,647 通过、1 个既有跳过，根构建和客户端翻译/TypeScript/Vite 构建通过。
新增通知偏好顺序测试在修复前复现失败，修复后通过。最初几轮页面测试因夹具
缺少 Capacitor 导出、把 undefined 写成 null 而失败，已修正夹具；保留失败日志，
不把它们记成产品缺陷。

本轮没有接受 Android SDK 许可，没有编译完整 Android Plugin/Service、生成 APK，
也没有更新安装包。真机仍需验证：同时配对两台 Hub、后台及锁屏送达、通知点击归属、
进程被杀后恢复、真实分发器卸载/重装、FCM 切换和离线移除。签名、生产账号及部署
继续按原计划延后。

## Opus 结论如何处理

两轮均实际使用 `claude-opus-5-5`、请求 `xhigh`。第二轮约 13 分钟、59 个只读
回合，读到了过程中部分修改，因此不是不可变快照。它没有发现 P1，并指出 3 项
应在发版前处理的 P2；“未发现”不能推广为全面安全保证。最后这些 P2 的修复由主
代理实现和验证，没有宣称 Opus 再次批准了最后一行代码。

| 第二轮意见 | 最终处理 |
| --- | --- |
| P2：旧注册未认领时丢通知 | 启动即本地认领；尚未启动时保留无主机 legacy 通知。Java 测试验证认领前/后路由及伪造 hostId 拒绝，桥接测试验证不发 HTTP 即可认领。 |
| P2：失败注册被维护任务重新提交 | 新记录有持久 confirmed 门槛，Hub 成功后确认；失败回滚。覆盖普通失败、回滚存储也失败、维护仍运行的情况，保留原 FCM。 |
| P2：总开关隐式替换 UP | 总开关沿用现有 UP；显式“改用系统推送（FCM）”才切换。无 FCM 的 Hub 也可重新开启已有 UP。 |
| P3：旧失败事件粘住 | 忽略 register 返回前的旧事件，以当前代际和最新状态为准；定向用例通过。 |
| P3：删除失败提示不清楚 | 提示此主机推送已暂停，给出重试或通知设置清理路径。 |
| P3：清理按钮/分发器不可用提示 | removing 时禁用连接、提供继续清理；旧接口和分发器不可用有对应提示。 |
| P3：FCM 切换崩溃窗口 | Hub 写入前先持久停止旧端点；远端删除待处理时禁止切换。 |
| P3：仅本地清理不自动收尾 | 下次维护刷新可完成本地清理，不 DELETE 新 FCM。 |
| P3：未保存勿扰时间被提交 | 勿扰时间独立草稿，连接分发器不提交，点击保存才写入；界面用例覆盖。 |
| P3：权限弹窗堵队列 | 权限请求移到主机队列外；注册和后续回执仍在队列内。 |

首轮指出的单槽注册、JS/native 契约不一致、跨主机回调、锁、迁移、全局重置、
删除顺序、分发器约束和未访问主机维护均已接入修复。部分首轮意见针对的是尚未
写完的实现，不能算成已发布版本的故障，也不把它们与第二轮重复统计。

仍开放且不能由本次检查关闭的事项：

- 长期离线主机或无法认领的旧记录缺少单独的分发器清理管理入口。目前保留连接
  恢复/明确的本地移除/旧全局恢复路径；遇到迁移冲突时不自动删除旧数据。
- 移除主机后 Android 托盘里已经显示的通知还没有按主机清除；不会因此重建连接，
  但旧通知点击可能提示无法定位主机。这需要原生管理与真机验收。
- 真实 SDK 在卸载、Activity 重建、Doze、断网/被杀后的行为，FCM/APNs 后台送达，
  原生 Plugin/Service 编译及系统权限仍未验收。Java 注册状态机测试不能替代它们。
- Opus 对 HTTP epoch abort 后服务端顺序、旧发行版历史和用户主动从分发器注销的
  语义提出待验证假设，本轮未确认成缺陷。源文件没有被本次审查穷尽覆盖。
