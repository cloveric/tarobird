# DeepSeek：引导当前任务的身份与轮次边界

范围：TaroCub 管理的 DeepSeek Harness 0.2.0-rc.2。所有真实验收使用独立临时主机；浏览器手机视口不等于实体手机。未替换 r10 安装包、修改生产 Bot 或全局 CLI 配置。

## 行为

普通消息仍然排队；用户点「引导」才尝试补充当前任务。排队消息尚未执行时，显示「这条消息仍在排队，开始执行后才能引导。引导内容未发送」，保留草稿，两端同步拒绝回执。不会把补充送给占用 CLI 的自主目标。

旧 DeepSeek 入口使用 `session.prompt(mode: steer)`，该接口没有目标轮次条件，并且可以唤醒空闲 Agent，或把中止期间的输入改放到下一轮。单靠 Gateway 的运行对象检查不足以保证到达原生主机时仍是同一任务。

现在走已有的私有继承管道 `steer-prompt`，携带普通输入的 `sourceRpcId` 和当前原生 `expectedTurn`。原生进程内连续核对来源、轮次、运行状态及 `agent/pre-step` 提供的中止信号，然后通过原生 `agent.inject` 放到下一步；不唤醒 Agent，也不创建替代轮次。未知协议或缺少能力直接拒绝。

未被原生 inbox 取出的引导，在该轮次中止、错误退出、步骤拒绝或私有管道关闭时按消息 ID 清除。错误与步骤拒绝的清理发生在原生结束事件落盘之前，避免结束事件监听器禁止重入写入的问题。引导采用可持久化的专属来源 `tarocub-steer`；原生主机崩溃后恢复 Agent 时先删除旧引导。其他普通排队输入和别的会话不受影响。已经取出的补充不能撤回；CLI 接收不等于模型已采用，保留现有「CLI 已接收引导」措辞。原生任务稍后失败、被停止或拒绝步骤，都不能据此保证模型执行过补充。

明确的 queued / stale / not_ready / unsupported 拒绝由 Gateway 原样保存；不确定的传输结果仍显示待核对，禁止自动重发。现有飞书自动引导的策略不变，原生安全检查同样生效。

## 验收

- Chromium / WebKit，真实 Hub + DeepSeek：桌面发起有界工具任务，手机补充指令，结果按补充要求改变；原生记录只有一轮，确切引导请求被消费。两端有接收回执，未创建普通 delivery。
- Chromium / WebKit，真实自主目标：普通输入确实进入原生 inbox 后，手机点引导得到 queued 拒绝，两端看到原因，未触发原生引导。撤回该消息后目标继续，随后停止目标、停止普通任务、继续普通对话并刷新双端均通过。
- 独立原生边界测试：拒绝排队身份和错误轮次；在确切执行轮次接收补充后立即停止，补充从未成为原生 user/message；显式发起下一条消息得到正常回答，没有额外原生轮次。此项没有浏览器 UI。
- 独立原生故障注入：原生 turn-stopping 抛错、pre-step 拒绝并恢复已取输入，都在结束前清空 next-step，后续用户来源与回复正确且没有多开的空轮次。另一次先通过原生 durability checkpoint 确认引导落盘，再对测试子进程 SIGKILL；主机恢复后旧引导被清除，后续消息正常，原生历史仍只有两轮。
- 双浏览器模拟路径补充检查拒绝保留草稿、回执刷新后持久化、重复请求不重复作用，以及不支持引擎、附件保护和普通队列。
- 根项目 233 个文件、3,736 项通过、1 跳过，构建通过；客户端翻译检查、类型检查和构建通过。

实际 Opus 5.5 xhigh 审查（本地材料：`evidence/deepseek-steering-opus55-2026-10-04.md`）发现结束事件重入写入和拒绝原因不准确的问题，修复后完成以上回归和原生故障验收。审查针对修复前源码，不代表 Opus 又批准了最终补丁。

机器可读记录见 验收证据（本地材料：`evidence/deepseek-steering-2026-10-04.json`）。早期失败也保留：原生停止后不会自动唤醒此前队列，测试改为明确撤回探测输入并显式发送下一条；一次 Chromium 后续普通请求收到原生空完成而没有正文，该次整条流程记为失败。相同流程随后在 Chromium 和 WebKit 通过；未声称修复或排除提供方偶发空输出。

飞书自动引导在传输结果不确定时的旧有排队回退仍是独立待处理项；App 显式引导不会自动重发或入队。实体手机容器、弱网/后台切换仍未验收；目标用量与普通对话用量的精确分离仍待处理。此次代码与前端构建尚未重新打包进 r10。
