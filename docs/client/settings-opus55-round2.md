**结论：没有 P0。** 有 1 个必须修的 P1，另外 2 个 P1 需要先核实。

**已确认没问题：**
- 嵌套确认框的 cancel 在 React 里会向外层冒泡，已经用 target 判断挡住了。
- 保存时关闭按钮是禁用的，`requestClose` 也会拦截。
- 邀请二维码用的是已保存线路，不是草稿。
- 扫码后的 Hub 公钥锁定和旧线路名都会带进新设备。
- 当前设备不显示撤销。

**P1**
1. **原生关闭会绕开 React 状态。** `PreferencesPanel.tsx:62` 只处理了 `onCancel`。Chromium（包括 WebView2 和 Android WebView）有个规则：两次 Esc 或返回之间如果没有其他用户操作，cancel 就无法阻止，dialog 会被直接关掉。
   - 复现：改线路 → Esc → 在确认框里再按 Esc → 再按一次 Esc。
   - 结果：外层 dialog 已被关闭，但 `settings` 仍为 true。新弹出的确认框挂在这个已关闭的 dialog 里，可能看不见，页面却被锁住无法操作；之后点齿轮也打不开设置。保存中被强关也是同一个问题。
   - 修法：外层加 `onClose`，同样先判断 target。不是代码主动关闭时：有草稿或正在保存，就重新 `showModal` 并弹确认；否则调用 `close()`。
2. **（待核实）断开并重新配对不是原子操作**（`App.tsx:246`）。只要中间一步抛错（比如离线时清理推送失败），就断开不了；如果密钥已删而本地身份还在，重试会卡在同一步。断开重配恰恰常在连不上时使用。建议每一步出错都继续，最后一定执行 `forgetIdentity`。
3. **（待核实协议）中转的安全文案。** 如果中转终止 TLS、又没有端到端加密，「中转不保存完整工作区」会让人以为中转看不到内容，应写明「中转管理员能看到经过的流量」。如果有端到端加密，就直接写「中转无法读取内容」。

**P2**
- `PairingCode.tsx` 不在可读范围，没核实。如果它是透明 WebView 加原生相机的方案，全屏不透明的设置 dialog 会挡住相机，需要真机测一下设置里的扫码。
- 保存中切到其他分类，成功或失败提示都在隐藏的面板里看不到。建议保存期间禁用分类切换，或在导航项上标出失败。
- 有未保存草稿时，邀请区注明「二维码使用已保存线路」。已保存线路里有 127.0.0.1 这类本机地址时，提示新设备用不了。
- 首次扫码读到「通过其他 VPS 中转」时，地址框隐藏、中转折叠，用户看不出读到了什么，Hub 锁定也无法解除。加一行读取摘要和「改为手动填写」。
- 编辑线路时切到「通过其他 VPS 中转」，会悄悄删掉直连地址，应提示「保存后将移除直连」。
- `DeploymentGuide.tsx:36/38` 的部署摘要渲染了两次，读屏软件会重复播报。
- 文案：
  - 配对码页写的「设备管理」应改为「设置 › 设备与安全」。
  - 断开确认框补一句「授权记录不会自动撤销」。
  - 「主机」和「Hub」统一用一个词。
  - 我上轮建议的「只保护连接线路」容易被理解成安全防护，改为「只在线路故障时接替连接」。
- 配对码输入时先去掉非数字（粘贴「1234 5678」会被截断）。撤销确认里带上平台名，方便区分同名设备。

**取舍**
- 切换分类时保留草稿、用橙点标记、只在关闭整个设置时确认：合理。
- 部署方式会影响校验，不用「仅命名」的措辞：同意，上轮是我说错了。
- 中转行用序号做 key：输入是受控的，值不会错位，我上轮「错位」的说法过重了。剩下的只是焦点和行内局部状态的问题，不算阻断。真要换 key 也不用改协议，在编辑器里单独维护一份 id 数组、保存时去掉就行。
