# Public IP relay acceptance — 2026-10-12

The requested deployment connects an existing Mac Hub to a shared Ubuntu 26.04
VPS. The VPS only forwards encrypted traffic; Bots, history, attachments, CLI
credentials and the Hub identity remain on the Mac. No game deployment or Bot
migration was performed. Addresses, keys and private configuration are kept
outside the repository.

## Deployed arrangement

- A separate unprivileged systemd relay listens on public TCP 8443 and accepts
  the Mac's fingerprint-pinned mutual-TLS tunnel on TCP 7443. Its health endpoint
  is loopback-only. The service is enabled at boot.
- A dedicated Mac loopback HTTPS listener uses a trusted public-IP certificate.
  Its TLS private key never went to the VPS. The original LAN listener remains.
- The VPS certificate timer checks every six hours and reissues from the public
  CSR when less than three days remain. The initial certificate was successfully
  issued and the timer's unchanged-certificate path completed successfully.
- An hourly Mac LaunchAgent retrieves only the public chain over verified HTTPS,
  validates its IP, validity, key match and monotonic expiry, then atomically
  installs it. It defers restarting a busy Hub and does not start a stopped Hub.
  The unchanged-certificate run exited successfully. A future automatic renewal
  and rotation has not yet elapsed and is not claimed as live acceptance.
- The shared VPS's existing HTTPS service on port 80 remains available. Nginx
  now distinguishes plaintext HTTP-01 requests from TLS without displacing it.

## Verified

- Public HTTPS succeeds with ordinary certificate validation and no custom CA
  or TLS bypass. The public endpoint advertises the original Mac Hub identity.
- A fresh signed TLS-identity response matches the certificate observed on the
  actual public TLS socket, proving the relay preserves application TLS.
- A temporary approved device completed the public WebSocket challenge/auth
  exchange, history synchronization and authenticated conversation listing.
  It saw the original five Bots and nine conversations. No messages were sent.
- Unauthenticated conversation access returned 401. The temporary device was
  revoked and its formerly valid token then returned 401. Original devices were
  not revoked or re-paired.
- A controlled relay service restart recovered the Mac tunnel; public HTTPS and
  the signed TLS-identity check worked afterward. Existing game HTTPS still
  returned its original build identity.
- Focused relay regressions: 3 files, 27 tests passed. Standalone completion
  hook: build passed, 219 files passed, 2,853 tests passed and one skipped.

This is public-network and protocol evidence. It is not a physical Android/iOS
network-switch, background, notification or microphone acceptance result. The
Mac must remain powered on and online.

## Existing paired phone

1. Open **我的 → 设置 → 连接 → 编辑线路** on the existing saved host.
2. Select **本地电脑运行 Bot** as the deployment mode; retain the direct address.
3. Choose **添加 VPS**, enter the provided `https://VPS_IP:8443` address under
   **VPS 线路地址**, give it a recognizable name, then choose **保存线路**.
4. Wait for **已连接** and the VPS route name. Existing pairing and chat history
   remain attached to the same Hub. A new host or a new pairing is unnecessary.

Outside the LAN, the client tries its saved direct route first and then the VPS
route. A VPS route cannot keep Bots available if their Mac host is offline.
