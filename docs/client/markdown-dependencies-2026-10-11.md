# Markdown 按需加载与原生内存复测

2026-10-11。继续检查普通 Mac App 的内存，而不是以浏览器内存或构建大小代替原生 RSS。
本次没有修改模型运行、平台提示词、消息协议、TLS 或生产机群。

## 改动和故障修复

普通文字、表格、列表、行内代码及未指定语言的代码块只加载基础 Markdown 解析器。
整篇解析后，根据实际语法树加载公式或代码高亮模块；先公式再高亮，保持原有结果。
ES module Worker 的各个文件同时进入离线缓存，原生包也包含这些资源。

新增的模块加载边界需要独立恢复，不能继续复用所有 Worker 故障的全局熔断：

- 某个公式模块下载失败时，普通消息和正常的代码仍能排版。每个模块最多自动尝试两次，
  不是每条消息重新尝试；悬空下载有 5 秒超时，原有 15 秒 Worker 超时继续兜底。
- 失败内容仍可读，点击“恢复排版”后可恢复同类历史消息，无需重发消息。
- 混合消息即使公式成功、代码模块失败，也会释放其他已等待的纯公式消息。
- 旧请求的“已跳过模块”回执与实际下载失败分开，不消耗后来手动重试的新预算。
- 旧 Worker、旧版本内容和已卸载消息继续受隔离保护。

14 个基于旧解析器生成的黄金样本逐字比较输出，覆盖表格、列表、公式、代码、引用、
脚注、危险链接和原始 HTML；URL 限制、KaTeX trust=false 与 1 MiB 输入限制保持有效。

## r39 原生基线与解释边界

在修改前的普通 r39 App 中，分别记录：

| 阶段 | 合计 RSS | 限制 |
|---|---:|---|
| 已打开的离线对话 | 270.30–278.14 MiB | 探索样本，前序交互状态不固定 |
| 空话题 | 177.81–199.33 MiB | 不代表实际聊天工作负载 |
| 从空话题打开本周阅读清单，46 秒内 | 102.27–217.77 MiB | 同一未修改版本也会随阶段和系统回收下降 |

旧基线按新启动 App、对应 WebContent 和 Networking 的 RSS 合计，未混入旧 debug App。
本次 r40 启动另观察到独立 GPU 进程，新样本把它也算入，因此两版不能直接做总 RSS
下降百分比。旧样本没有完整 GPU 归因，也不能据其低值声明整个 App 的内存达标。
上述原始样本见 `r39-*.json`。不能把 r39 自身的空闲回落归因于本次代码，也不能
选最低值关闭原计划 200,000,000 字节门槛。正式冷启动计时仍未完成。
