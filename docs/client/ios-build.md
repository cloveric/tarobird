# iOS builds and TestFlight

TaroBot uses the shared mobile client in a Capacitor 8 iOS shell. The iOS App
connects to authorized hosts; it does not run the Hub or local model engines.
This packaging work adds no host capability or headless CLI command. Android,
desktop and the standalone CLI keep their existing release paths.

## Prerequisites

- macOS with full Xcode 26 or newer, the iOS SDK and an iOS Simulator runtime.
  Command Line Tools alone cannot build this App.
- Node 24 or newer; install the root and client lockfiles with `npm ci` and
  `npm ci --prefix client`.
- Simulator builds use local ad-hoc signing and need no Apple account. Do not
  disable code signing: Xcode also uses this step to embed the simulated
  application identity required by Keychain. TestFlight requires an active
  Apple Developer Program membership, an App Store Connect app record and
  signing assets for both the App and its share extension.
- Set `DEVELOPER_DIR=/path/to/Xcode.app/Contents/Developer` to use a particular
  Xcode without changing the machine-wide toolchain. `--output` may point to an
  external drive; DerivedData, package checkouts, module cache and build scratch
  files go inside a new per-build directory there. Xcode components and Simulator
  runtimes have separate OS-managed storage; this flag does not relocate them.

```sh
npm run ios:doctor --prefix client
npm run test:ios-release --prefix client
npm run ios:build --prefix client -- --mode simulator --output /path/to/builds
```

The build always rebuilds the frontend and runs `cap sync ios`, including the
mobile CSP copy hook. It validates the packaged App and share extension names,
IDs, versions, platforms, privacy manifests and bundled assets. A successful
simulator receipt explicitly says `physicalDeviceVerified: false`. The App path
in that receipt can be installed on a booted Simulator with `xcrun simctl install`.
Compilation alone does not verify native permission prompts, background push,
sharing from another app, or real-host networking on an iPhone.

The simulator identity is generated by Xcode for local testing. It is not a
distribution identity, cannot install this build on an iPhone, and does not
verify production APNs or provisioning.

Swift packages are pinned by the committed `Package.resolved`; builds refuse
implicit dependency upgrades. After an intentional Capacitor/plugin upgrade,
refresh the lockfile with Xcode's package resolution, review the changed pins,
and commit it together with the JavaScript lockfile changes.

## Signing and export

The owner-authorized native identity change uses these identifiers:

| Component | Identifier |
| --- | --- |
| App | `com.tarobot.client` |
| Share extension | `com.tarobot.client.share` |
| Shared inbox App Group | `group.com.tarobot.client` |
| URL scheme | `tarocub` |

This is a new iOS App identity, not an update to `com.tarocub.client`. Create a
new App Store Connect record and profiles; the old uploaded App record cannot
change its bundle ID. Fresh installation requires pairing again. Register the
new App Group and associate both targets before exporting. The App declares its
own bundle ID as its APNs topic to Hubs that advertise `apnsTopics`; keep the
Host's `push.apns.topic` for the old App and add `com.tarobot.client` to
`push.apns.topics` ([APNs topic routing](apns-topic-routing-2026-10-29.md)).
Against an older Host the new App does not register for APNs.
See [identity migration and release gates](native-app-identity-2026-10-28.md).

Both targets need the same developer team and App Group entitlement. The main
App also needs Push Notifications. Configure the identifiers, group association,
signing certificates and provisioning profiles in the developer account/Xcode.
If an identifier belongs to another team, stop and resolve ownership; do not
silently change bundle IDs or the App Group. Keep all credentials, profiles,
account/team details and signing logs outside Git.

```sh
npm run ios:build --prefix client -- --mode testflight \
  --team ABCD123456 --build-number 1 --output /path/to/builds
```

The team above is a placeholder. Use the real team privately. The marketing
version comes from `client/package.json`. An explicit build number is required
for TestFlight; increase it for every upload of that version (supported range
1–9999). Both targets receive the same values, so changing the client version
cannot leave the share extension behind.

The command archives Release, exports with `app-store-connect`, then unpacks the
actual IPA and verifies both signatures, version/platform/identity consistency,
the shared App Group, production APNs and absence of the debugging entitlement.
It writes `receipt.json` with the IPA SHA-256 only after those checks pass. The
script does not create certificates, change signing permissions or automatically
enable `-allowProvisioningUpdates`. Missing profiles fail the build explicitly.
Exported signatures still require Apple's server-side validation.

## Upload and acceptance

Upload the verified IPA with Apple's Transporter, or distribute the matching
archive from Xcode Organizer to App Store Connect. The build script deliberately
does not upload or automatically enroll/purchase a developer membership. Record
the version, build number, uploaded digest and Apple's processing result before
inviting testers. An export receipt is not a TestFlight delivery receipt.

Before calling the iOS version ready, verify on a physical iPhone:

1. Clean install, pairing with a real host and LAN/relay reconnection.
2. Text, images, files, voice, question cards, queueing and stop/resume.
3. Photo/camera/microphone/local-network/notification permission flows.
4. Share extension importing files/text into the correct conversation, including
   cancellation and retries; save/export from the App into Files.
5. Production APNs registration, background/locked-screen notification delivery,
   sound, conversation preview and tap-to-open routing. Configure the APNs key on
   the private Hub only, with `sandbox: false` for TestFlight. Never bundle it.
6. Upgrade preserving pairing/identity and local records. Verify iPhone and iPad
   layouts separately; the desktop-only ADHD board stays unavailable on iOS.

TestFlight updates are distributed through TestFlight, and public App Store
updates through the App Store. The Android APK updater is not an iOS update path.

Public App Store submission is a separate workflow. See the
[2026-10-25 readiness report](app-store-readiness-2026-10-25.md) for the observed
store metadata gaps, privacy requirements and proposed isolated review access.
Uploading a build does not grant reviewers access to an owner's production Hub.

References: [Capacitor environment](https://capacitorjs.com/docs/getting-started/environment-setup),
[Apple build upload](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds/),
[TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/).

Build output (DerivedData, archives and unpacked IPA checks) is normalized below
a physical `.noindex` directory; the default is `client/ios/build.noindex`. Read
the printed output path when passing a legacy `--output` location.
