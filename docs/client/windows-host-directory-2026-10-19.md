# Windows Host 目录重定向与本机控制恢复（2026-10-19）

## 根因与证据边界

Windows MSIX 全信任应用的子进程可能继承包身份。名义上的
`%APPDATA%/com.tarocub.client/host` 与资源管理器启动的桌面程序使用相同字符串，
却可能读写不同文件视图：前者新文件进入当前包的
`%LOCALAPPDATA%/Packages/<package-family>/LocalCache/Roaming/com.tarocub.client/host`。
Microsoft 的 [MSIX 文件虚拟化说明](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes)
明确描述了 AppData 的私有写入与合并读取。不能仅凭路径字符串或 realpath 相同认定数据相同。

Owner 已在真实 Windows 上确认这个原因，并完成离线校验复制、保留原身份、改名旧目录备份；
停止后台后重新打开桌面 App 也恢复成功。本任务不再迁移该机器，也不重新初始化。

本机隔离回归另外证实：旧桌面 start 在已有数据库而 identity.json 缺失时，确实会启动并生成
替代身份。新增测试在修复前失败；目录问题与客户端恢复定时器漏做本机凭据验证是两个独立缺口。

## 修改后的行为

- 桌面、headless CLI、初始化、直接 hub run、服务启动与冻结运行组件交接，均在读写状态前执行共同准入。
- 复用静态 CRT 的 `tarobot-host-launcher.exe` 增加只读检查模式，按实际 Node PID 查询 Windows
  包身份，同时返回不重定向的 Known Folders 和句柄路径；不依赖 PATH、用户名、某个商店包名或运行时 C# 编译。
  调用超时 5 秒、输出最多 512 KiB，严格解析 JSON。探针缺失或失败时拒绝继续。
- Windows CLI 默认目录来自系统 Known Folder，与原生桌面一致，不把继承的 APPDATA 环境字符串当权威。返回桌面使用的名义 Known Folder 路径；文件标识用于核对实际位置，避免别名/大小写导致 TLS 路径匹配变化。
  `--state-dir` / `TAROBOT_HOST_DIR` 仍可选择独立主机，但也必须通过准入。
- 包身份存在时拒绝 Host 命令，包含可能登记控制器的只读管理命令；允许帮助和只读 directory plan。
  提示改从开始菜单打开桌面 App，或从非打包的普通终端运行 CLI。不自动脱离沙箱启动第二个 Hub。
- 仅扫描各包精确的活动 Host 路径，不扫描改名备份。上限 2,048 个包、3 秒检查预算；未知访问失败阻止创建。
  工作区文件单独产生的隔离目录会列为 shadowWorkspaces，不阻止完整真实 Host；但真实 Host 核心文件也缺失时仍禁止据此造新身份。有隔离数据而目标缺失时报 shadow_only；两边活动目录均存在数据、或 SQLite 文件集分散时报 conflict。
  即使身份相同也不猜选、不合并。已改名保留的旧目录不会阻止已恢复的主机。
- 已有数据库缺身份、已有身份缺数据库、遗留 Bot/启用记录而核心状态缺失时不补造身份。
  `hub run` 仅启动已初始化的目录。首次桌面 start 和 CLI init 走同一初始化路径。
- Windows 的目录准入管道在初始化/Hub 生命周期前取得；已有主机的身份管道在打开数据库前取得。
  文件锁因虚拟化分成两份时，内核管道仍阻止新版本重复实例。缺本地控制密钥也会探测旧控制管道，
  不能直接当作后台不存在。旧探针组件在打包校验时被拒绝；新版本拒绝交接给缺少 `windows-state-admission-v1` 能力标记 的旧冻结组件。
- 安装器和服务原生入口也拒绝从打包进程执行重置/启动，避免在错误视图写入。
- 本机处于待恢复状态时重跑 resume → 原身份匹配 → 原生安全凭据证明 → 刷新连接池；不改用显式 start，
  不重启已运行 Hub，不启用用户停用的主机。恢复结果带生命周期和身份检查；过时结果不能覆盖后来配对。
  健康连接只做 resume，不重复配对；瞬时探针/后台错误不会关闭健康连接。明确身份变化立即停止本地连接。相同公钥的新配对也通过代次栅栏废弃旧恢复结果。
  身份变化不会自动覆盖原来记住的主机公钥；失败时仅暂停已识别的本地主机，远程主机保留。
  本地身份完全未知时保持原有 fail-closed 边界，不能猜测哪个旧配对是本机。

## CLI 与诊断

```text
tarobot directory plan --json
tarobot directory plan --state-dir <目标目录> --json
tarobot directory verify --from <离线原目录> --state-dir <恢复副本> --json
```

plan 不打开 SQLite，不修改数据；显示目录分类、身份公钥摘要、SQLite 旁文件和后台服务注册情况。
verify 检查完整文件 SHA-256、原身份文件字节和数据库字节；运行中/未知 PID、符号链接/联接、
文件变化、上限超出均拒绝。最多 100,000 项、20 GiB、每遍 120 秒；仅忽略实例锁及控制密钥。
差异返回 verified=false 和非零退出码；不能把身份相同当作数据相同。
这些命令不会应用迁移。诊断信息及校验清单含本机路径，应私有保留，不粘贴到公开 issue。

停机、状态、日志及卸载旧服务使用较低级准入：仍核对非打包进程与原生文件视图，但不因双目录或部分状态阻止安全收尾；创建/启动/重启/初始化仍保持完整检查。无法证明非打包上下文时不绕过。临时 probe_failed 返回退出码 1，允许现有有界退避重试；明确目录冲突返回 78。

UI 只显示结构化分类，路径和密钥不传入 WebView。分类包含 redirected、shadow_only、incomplete、
conflict、probe_failed、foreign_runtime、runtime_update_required，另区分目录缺失、后台未就绪、
设备安全凭据验证失败、显式停止与主机身份变化。启动 marker → Rust → UI 的允许列表同步维护。

## 旧安装安全恢复与回滚

此过程用于尚未恢复的旧安装；已恢复且正常连接的机器不执行。

1. 从普通桌面/非打包终端运行 plan，记录真实目标、活动隔离源和身份摘要；不要根据用户名猜路径。
   多个源、双目录不同数据、分散的 SQLite 主文件/WAL、服务状态未知都停止自动处理，保留全部副本人工核对。
2. 在原有入口停止后台及 Bot，退出桌面 App，禁用或卸载原有自动启动/任务计划注册；
   活动控制管道、Hub/Bot 锁 PID 或不明任务仍存在时不能复制。不要删除锁来伪装离线。
3. 在普通进程上下文建立完整的私有离线备份，保留 identity.json、数据库及其旁文件、Bot 与工作区内容，
   记录文件清单和 SHA-256。遇到联接或源目录中指向外部的数据，先人工核对，不遍历/覆盖外部目标。
   已配置的绝对路径应仍指向原名义目录；若实际保存了隔离目录路径，不做字符串批量替换。
4. 目标必须不存在。目标有任何身份或数据时不覆盖、不合并；即使看似空主机也保留并人工决定。
   先复制到目标同卷的新暂存目录，运行 verify 对照离线源。验证失败保留现场，不启动。
5. 校验通过后，将活动旧源改为唯一备份名，原始字节不删除；将验证过的暂存目录原子改名为真实目标。
   切换时仍保持所有写入进程停止。旧商店应用清理/卸载可能清除 LocalCache，因此应另留一份独立备份。
6. 用新版本再运行 plan，然后启动一次；核对公钥摘要、原主机名、Bot/对话数据、实际进程与入口。
   再执行后台停止后的 App 冷启动，确认仍是同一身份。不得再次运行旧包内的 Host 启动入口。
7. 若启动前失败：确认没有运行实例，移走失败目标为另一份保留目录，再把原备份改回原名；不覆盖新出现的数据。
   若恢复后已经产生新消息/文件：先停机备份新目标，不能直接用旧快照覆盖回去；需人工比较，避免丢失新数据。

自动 apply/rollback 暂未提供：目录内可能有绝对工作区引用、外部文件和旧版本运行组件，
没有证据时自动迁移比保留并报告更危险。只读 plan/verify 与明确的离线、保留备份、原子切换步骤构成恢复方案。

### 实现复审发现与处理

- 修复了 Opus 复现的严格更新清单不兼容：能力标记改用可扩展列表，旧 CLI 仍能解析更新元信息。
- 修复初始化准入过早释放、旧 headless 目录保护遗漏、恢复时内存身份保护遗漏。
- 采用 B1/B2/B4/H1/H2/H3：安全停机与启动分级；工作区隔离副本和 Host 核心状态区分；探针失败有界重试；健康连接不重复配对；停机未确认时保留管道所有权；已初始化主机的 init 只读返回。
- H4 仅在完全没有已保存连接时放行客户端模式并显示诊断；存在可能的旧本机记录而身份未知，仍不绕过原生控制证明。
- 采用 M1/M2/M3/M5/L1-L5 中对应修正：已验证管道状态、文件标识比对、相对路径转绝对、逐源元数据错误、明确 foreign_runtime、名义路径一致、同类提示关闭后不重复弹出、空目录分类、同公钥配对代次防护。
- 开发检查：Windows 源码运行前先执行 `node scripts/build-host-launcher.mjs --output bin`，缺组件会明确失败，不回退到不受保护的启动路径。

以下建议没有直接采用，原因及边界保留给 Owner：

1. B3 建议显式 init/start 时，依据“空数据库且缺身份”补建身份。数据库行数为空不能证明外部设备从未信任原公钥；本任务明确要求不得在原身份不可见时静默重建。因此保留 incomplete，并修改文案以兼容首次初始化曾失败的情况。确实是从未完成的首次安装，应先保留离线备份，再经现有明确确认的「全新开始」流程处理，不自动判定。
2. B4 建议忽略其他包的权限拒绝。无法读取的隔离路径可能就是旧主机所在处，忽略后新建会违反本任务核心边界；继续 fail closed，但改为可退避重试，不永久退出监督服务。
3. M4 建议增加任意大清单的 CLI 上限调整。本版保留固定上限并明确失败，不提供绕过；超大目录需在受监督的离线流程生成独立完整清单，不能把部分校验当成功。逐源元数据异常已改为独立报告，不吞掉其他候选。
4. 明确不同身份或核心数据冲突时立即暂停，未采纳“重复两次再暂停”的建议；瞬时探针和后台错误已单独处理，不影响健康连接。

### 明确保留的边界

- 实际 Windows/MSIX 进程视图、新安装包安装与冷启动尚未在真机执行。本次交付为源码修复，未发版或替换已安装 App。Owner 先前的真实恢复证据用于根因确认，不计为新补丁验收。
- 当本机身份完全未知而已有旧配对记录时，无法证明哪个是旧本机控制身份，继续暂停启动连接池。空记录的客户端可以先显示诊断；若保留目录问题又配对远端，下次启动可能进入这一边界。未来需依据每条原生 Identity 的部署来源精确分类，不能仅凭主机名称猜测。
- 不可读的隔离候选仍显示 probe_failed 并退避重试；目前不会在 UI 或 plan 中暴露出错候选的具体路径。精细 CLI-only 定位属于后续改进。
