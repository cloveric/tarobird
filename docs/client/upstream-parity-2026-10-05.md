## 已复现并修复的问题

DeepSeek 返回 `Content Exists Risk` 时，客户端原先归类为 `engine-cli`，给出通用
引擎故障反馈；协作调用也缺少对应的不可自动重试分类。移植上游回归用例后，先
观察到两个失败，再修改实现。现在 App／飞书／Telegram 会说明这是模型对本轮
内容的拒绝，提示用户检查请求或上下文，而非把它当作需要重启的进程故障。
Bus 返回 `engine_content_policy` 和 `retryable: false`。

分类检查先于鉴权错误，因此含 `Authentication required: 403` 前缀的同类拒绝
也不会触发 Telegram 的认证刷新、清空会话或原样重放。附加在末尾的 MCP 启动警告
仍不参与主错误分类。

父代理还发现了上游移植之外的遗漏：审计摘要的合法分类列表不包含新分类。
当记录的显示文字为中文时，已落盘的分类会被降为 `unknown`。新增真实文件
写入／读取测试先复现该失败，再补齐列表；现在运行记录保留正确分类。

DeepSeek 的旧 `telegram-*` ID 可能本身就是持久化的原生会话 ID。按前缀一律换新
会丢失原有上下文，所以沿用客户端的缺少绑定才分配新 ID 的机制。现有
SessionManager、Bridge 锁内解析和 DeepSeek 适配器用例均通过；之前的真实 CLI
重置、绑定和切断证据见[会话验收](native-session-mobile-2026-10-04.md)。本轮没有
通过故意触发真实模型拒绝来验证提供商策略。
