# macOS 1.0.100 signing compatibility repair

Status: [macOS 1.0.100 is published](https://github.com/cloveric/tarobot/releases/tag/macos-v1.0.100). Local installation is staged and waiting for active work to finish.

macOS 1.0.98 and 1.0.99 re-signed their bundled Node with Hardened Runtime and
`allow-jit`, but omitted the permission needed to load native modules signed by
other developers. DeepSeek Harness 0.2.1-rc.2 failed before its model request:
macOS rejected its `node-addon-require-builtin` binary because its signing team
was different from the Node process. The loader's final `MODULE_NOT_FOUND`
fallback obscured the original rejection and the App showed a generic restart
message. Restarting alone does not repair the signed binary.

This is a Mac packaging repair. The desktop App is 1.0.100; Host/standalone CLI
remain 0.1.447 and database schema 21. The unchanged canonical CLI archive is
reused byte for byte from the 1.0.99 release, SHA-256
`f83f65a9aab62acb7a9c7bbe0a8406ee7fc59467abfa64d0a958768112e33225`.
The bundled Host source remains `62fb3089f90c7475d76f05fdb3bbbbebcec82720`;
the desktop version and signing policy have separate source-controlled changes.
Android, Windows and iOS remain at 1.0.99. Their engines do not execute under the
macOS library-validation policy. CLI command/API semantics are unchanged.

Only the bundled Node receives `com.apple.security.cs.disable-library-validation`
alongside `com.apple.security.cs.allow-jit`. The App main executable retains
library validation. Developer ID signing, Hardened Runtime, secure timestamps,
Apple notarization and pinned updater signatures remain required. No debugging,
DYLD environment or unsigned-executable-memory exceptions are added. This is
[Apple's documented entitlement for third-party plug-ins](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation).

## Reproduction and independent review

The root investigation and actual Opus 5.5 xhigh independently compared the same
third-party binding with the installed Node, the old 1.0.97 Node and isolated
copies. Installed 1.0.99 failed; changing only the library-validation entitlement
made loading succeed. Opus additionally exercised eight external arm64 native
addons, JIT and an FFI callback. All eight were rejected before the repair and
loaded after it.

A `dsh --version` check succeeds even with the defect, so version output is not
engine acceptance. The prior release's sqlite3/canvas checks also passed because
those bundled modules shared the App's signing team. The release gate now needs
an independently signed external native-module fixture as well.

The real installed DeepSeek Harness, through the unchanged production adapter
and an isolated home/session, returned the expected `DEEPSEEK_RECOVERED_OK`:
first using the minimally repaired test Node (3.9 seconds), then using the
Developer ID signed candidate App's Node (3.5 seconds). These are real provider
responses, not mocked engine output. The production DD1 conversation has not yet
been retried; this evidence alone does not establish local installation.

- Published source/signing policy: `0d18d83f3fc21e8dfc20d3c2162718e36f83f6cc`.
  Native compile inputs were `db281e10e8527c9c0a27f3ccdb11deed33f86a17`;
  the later commit adds only signing/verification tooling and docs, with no change
  to the compiled application or bundled Host inputs.
- App and DMG accepted by Apple, stapled and accepted by Gatekeeper; strict
  signatures and exact Node/App entitlement sets verified.
- Mounted DMG and extracted updater App matched across all 5,041 file/link/mode
  entries. Both final Nodes loaded the real external DSH binding and a newly
  compiled, independently ad-hoc-signed Node-API fixture.
- All six published assets were downloaded and matched against local bytes,
  GitHub digests and SHA256SUMS; the updater signature and manifest asset URL passed.
- Native updater on a copy upgraded 1.0.99 to 1.0.100 while keeping Host 0.1.447:
  tampered signature rejected, replacement Host restarted, identity, paired
  controller, conversation and file retained. This is a real native installer
  with synthetic data, not the production replacement.
- Production: the staged App and sealed rollback backup were verified byte for
  byte. The guarded installer is waiting for the current turn and other accepted
  work to finish. It will take an offline state backup, replace the App atomically,
  verify the installed DSH addon, and queue one follow-up verification. Production
  DD1 reply/UI acceptance remains pending until that follow-up. No forced restart.
