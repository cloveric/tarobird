# 1.0.116 release verification

Status: Mac, Windows, Android and the canonical CLI are published and their
downloaded bytes are verified. iOS 1.0.116(1) is VALID / IN_BETA_TESTING and assigned
to the existing internal test group. Local Mac App 1.0.116, Host 0.1.461 and
terminal CLI 0.1.461 are installed and verified. The installed runtime returned
a real model response, and the normal native GUI window was visibly verified.

Release source: `c7c84ec6907379041393c88e58660e6af4708603`.

## Scope and compatibility

- Baseline: App 1.0.115 / Host and CLI 0.1.460, source `4fcfc997960f63b79a7a9111b669f1b5415eb86d`.
- Release: App 1.0.116 / Host and CLI 0.1.461; Android versionCode 2026102702; iOS build 1.
- Protocol 1 and Hub schema 22 remain unchanged. This release introduces no database migration, compaction, or backup-policy change.
- The changes are App presentation and navigation: light warm-grey setup buttons and accent, lighter sage accent, red unread indicators (desktop dots, phone avatar counts), recording/reply accents, compact phone queue, and consistent settings labels and controls.
- ADHD uses a flat reading surface and a single fine pane border. Group topics start collapsed on each visit; searching can reveal them without changing ordinary-chat folding. Long reply-source excerpts truncate within the pane while retaining source navigation. Desktop Bot identity sits next to the conversation title. Agent Bus and Return to chat retain their controls without permanent button frames.
- Audit fixes preserve pending question/approval visibility on folded ADHD groups and keep pinned topics reachable in the ADHD picker; restore left-aligned, content-sized reply-source links without reintroducing long-text overflow; and improve non-monochrome recording timer contrast. See [the audit record](../client/day-ui-audit-2026-10-27.md).
- There is no new CLI command or Host capability. The canonical CLI still advances because it includes the same rebuilt web client and must match the App-bundled Host package.

## Source verification

Root and Claude Opus 5.5 xhigh independently reviewed the changes since the baseline. Opus identified six confirmed UI issues and reviewed release safety bindings; root also found the pinned-topic regression. The final root complete gate passed 506 JavaScript test files / 6,887 tests, with five conditional skips, plus 77 native desktop tests, Host/client builds and repository checks.

The initial broad browser matrix passed 147 Chromium tests; WebKit passed 142
with three guarded skips and two test-loader readiness failures, subsequently
corrected and rechecked. The final topic matrix passed 14 cases per browser.
Final reply-source and theme tests passed 26 Chromium and 25 WebKit cases (one
guarded WebKit skip). Narrow-sidebar and resize checks passed five cases per
browser. Final topic/forced-colors coverage and the final packaged-frontend
smoke check each passed in Chromium and WebKit; WebKit does not emulate forced
colors. These counts overlap and must not be added into one total.

The first candidate was superseded before publication after the narrow-sidebar
issue was reproduced. The final complete source gate ran on `c7c84ec6` and passed
all counts above. A subsequent package gate detected frontend chunk differences
caused by symlinked dependency installations. Both dependency directories were
replaced by independent lockfile installs; the JavaScript/runtime dependency
bytes matched the tested installation (apart from installation metadata and the
Android preparation patch). All final packages were then rebuilt in a fresh
release output directory. The final canonical CLI, desktop renderers and mobile
frontends agree byte-for-byte. No superseded package or publication receipt was
used for the release.

GitHub checks on the final source did not start because of the account
payment/spending limit. Local checks are independent evidence; GitHub CI did not
pass or execute the source suite.

## Local activation and remaining boundaries

The terminal CLI has been switched to the verified 0.1.461 package. Its wrapper
and Node runtime are unchanged, its external addon loads, and the previous
0.1.460 package remains available and byte-unchanged. This does not update or
restart the running App-managed Host.

Local Mac activation completed through the native safe-drain mechanism after
active work finished. The installed App is 1.0.116 and its running Host is
0.1.461. The App and bundled Node hashes match the published signed package;
terminal CLI read-back is also 0.1.461. No forced stop, database compaction or
schema rollback was performed.

The first local activation ended with `desktop_update_cancelled` before App
replacement. The old App remained installed, and the update session restored
the old Host normally; this is a failed activation, not an installed release.
The terminal CLI update remains independent and valid.

A controlled replay using the installed BotManager shutdown methods and the
frozen desktop-update session reproduced this failure: after an accepted
guarded stop, the Host briefly reports `draining=true`, `drained=true` with its
drain ID cleared. The supplemental release-helper monitor rejected that normal
shutdown transition and cancelled the session. The original failure receipt
did not retain the monitor's exact error, so this replay establishes a concrete
failure path rather than a complete trace of the original incident.

The local helper now recognizes only this fully drained, same-process,
same-identity teardown after observing the owned drain. The packaged update
session still requires its atomic guarded stop and actual old-process exit
before allowing App replacement. Busy work, changed identities/drains, unknown
counts and ordinary cancellation still fail closed. Monitor errors are now
retained in failed receipts. Forty-five isolated admission checks passed,
including reproduction of the previous failure, successful guarded handoff and
rejected-stop protection. No production state was touched by these tests.

The failed attempt and original scripts are archived. The staged App and old
App backup were reverified against their original tree hashes and signatures;
the live identity, schema and backup policy are unchanged. The deliberate retry
completed using those same artifacts. This helper repair changes neither the
frozen source nor the published package bytes.

Post-install acceptance passed on 2026-10-27:

- Runtime read-back confirmed the new Host process, preserved identity and
  production temporary directory, authenticated reconnect and all seven managed
  Bots online. Every pre-update Bot, conversation, message, device and attachment
  ID was retained; newly arriving messages were not mistaken for lost records.
- Hub schema remains 22, storage mode is unchanged, and the owner's existing
  zero-day automatic-backup setting is preserved. The one-time update recovery
  snapshot is separate from that automatic-backup policy.
- The installed signed bundled Node loaded the external DeepSeek addon and
  received the exact real response `DEEPSEEK_INSTALLED_OK` in an isolated model
  session. This test did not create a production conversation.
- The App was opened through normal LaunchServices. Native UI inspection and
  screenshots showed the connected conversation window, the General settings
  page reporting 1.0.116, and successful return to the original conversation.
  No preferences were changed. This verifies visible GUI startup and basic
  navigation, not every desktop interaction or real mouse window dragging.

The original helper receipt remains unchanged. Final acceptance is recorded
separately in `local-acceptance.json`, backed by runtime, model and GUI receipts
