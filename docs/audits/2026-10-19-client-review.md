## 拖入文件

确认存在两个不同问题：桌面主窗口没有关闭 Tauri 原生拖放拦截，而前端只在输入框接收 HTML 拖放；因此向消息区域或 ADHD 窗口主体拖入文件不能加入附件。Tauri 当前配置 schema 明确注明：Windows 前端使用 HTML5 拖放时需关闭原生 `dragDropEnabled`。

修订如下：

- 主窗口设置 `dragDropEnabled: false`，让 WebView 的 HTML 文件事件进入现有附件链路。
- `client/src/attachment-drop.ts` 只接受真实文件事件和浏览器给出的 `File` 对象，不新增任意本地路径读取命令、IPC 或文件权限。
- 接收区域扩大到当前可用的对话主体；有弹窗、处于搜索/归档/只读/删除多选、草稿尚未载入或正在上传时不接收文件。旧输入框监听已移除，避免重复添加。
- ADHD 每个对话各自接收自己的落点，内部文字拖动不会被当成附件；浅色描边提示当前文件落点。
- 拖入后加入当前草稿附件，按“发送”后沿现有上传接口提交；不会因为拖入就自动发送任务。

独立 Opus 复审后补了窗口边界：全局 capture 在 `main.tsx` 启动时安装（并含 HMR 清理），未配对/锁屏阶段也只对文件阻止 WebView 默认导航，侧栏/空白处显示不可放入，事件仍交给实际落点；多个 ADHD 窗口不会各自拦截并重复添加。已隐藏或 inert 工作区里的打开状态 dialog 不再阻塞当前对话；真正显示的 dialog 仍阻止背景落点。文件夹按 entry 类型拒绝并提示选其中文件，零字节文件不会被误判为目录；上传中/归档等拒绝场景复用现有提示区域。原有上传策略仍拒绝空文件，测试单独核对其可进入草稿后移除，并未把“可进入草稿”写成“已成功上传空文件”。

Chromium 和 WebKit 的自动操作均验证了：向消息区拖入文件、只出现一份附件、发送后 Hub 收到附件块、ADHD 两窗落点隔离、普通文字拖动不添加文件。配置契约测试覆盖主窗口关闭原生拦截。本轮没有实际 Finder/Windows 外部程序发起的原生拖放收据，仍须在新安装包验证。

进一步的原生排查补上 Tauri `file-navigation-guard`：原生导航回调拒绝 `file:`，即使来源提供的是文件 URL 而不是 DOM `Files`，也不能把 App 主文档替换为本地文件；不读取文件路径、不增加 IPC 或 filesystem scope。该回调已通过实际 desktop binary 的 `cargo check --locked`。排查中 Cocoa 夹具最初只写 `NSURL` pasteboard，可能属于 URL 拖动，不能把它默认导航的结果直接当作 Finder 文件拖放失败。后续真实原生验收收据由总报告记录。

依据：[Tauri 配置说明](https://v2.tauri.app/reference/config/#windowconfig)、[维护者对 DOM 与原生拖放互斥的说明](https://github.com/tauri-apps/tauri/issues/14373)、[原生导航回调合同](https://docs.rs/tauri/latest/tauri/plugin/struct.Builder.html#method.on_navigation)；同时核对本地锁定的 Tauri 2.12.1 / Wry 0.57.0 源码。浏览器之外的真实落点数据若不产生 `File`，需要新的窄授权桥接设计，不能用开放任意路径读取来替代。
