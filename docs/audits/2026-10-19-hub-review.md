## 恢复审阅补充：诊断读取与推送回执

本次以 `8af7df1` 为基线恢复暂停项，不接触生产数据库、不重启主机。

- **诊断历史挤占实时写队列：确认并修复。** 先失败回归用一个尚未提交的写事务复现诊断页无法返回。现在每个 Hub 最多一个独立只读 WAL 连接，通过 `BEGIN` 固定一个已提交版本，每批 250 条、只保留一页与有限统计集合。完整类型、结果筛选、匹配总数、最后成功/失败时间和脱敏保持原契约；并发新增或维护删除不会使同页统计混合两个版本。
- **读取生命周期：补齐取消与清理。** HTTP 断开/主机关闭取消正在进行的扫描；尚在诊断队列中的已取消请求不会打开数据库。打开、事务开始和查询失败均释放读连接，后续请求可继续。响应前仍用实时写连接重新检查 owner 和设备撤销状态，快照不是旧授权通行证。真实本机 HTTP 回归覆盖读取期间撤销、关闭时取消剩余批次，以及先释放读连接再关闭主数据库。
- **清理推送运输行后重复通知：确认并修复。** 原先七天终态清理也删掉唯一去重依据；相同消息的晚到编辑可重新通知。`sent / suppressed / cancelled / failed` 四种情况均先复现。新增不含正文的紧凑 `push_receipts`，与消息/outbox 同事务写入；升级与清理前回填旧运输行，旧兼容写入器也受数据库去重触发器保护。新消息、同一消息的另一类真实通知仍正常入队；重复刷新不重新触发通知。
- **保留边界：** 已永久撤销的设备不会再参与推送，可清除其回执；个人删除和共享消息墓碑不被当作物理删除，保留去重依据。紧凑回执不按七天过期，仍随有效消息/设备数量增长；这不是把所有业务历史强行限制到固定大小。新表使用附加兼容结构，schema 19 不变。升级前若旧代码已经删除运输行，不能从已丢失的回执中恢复实际通知结果；本次保证保留下来的旧行与之后的新通知。
- **邻接测试修订：** 个人删除回归原先对所有事件直接读取 `payload.message`，遇到同步的队列变化事件会报错。查找现在明确限定 `message.deleted`，其余个人删除、成员隔离、重放与重启断言保留。
- **Opus A4 上传许可孤儿：确认，采用兼容旧写入器的保守修法。** 独立临时 Hub 复现附件 GC 后上传许可仍残留；原 meta 值仅有请求编号，哈希键不能恢复来源/附件关系。保留原 `{requestId}` 值，仅为全新许可建立独立关联表；附件 ID 有索引，`message_attachments` 插入触发器在消息事务内将其关联许可置为已使用，schema 19 旧写入器直接发送也会触发。新许可若已有附件引用则直接标为已使用；失败回滚，重复上传不重置，旧许可不推定未使用。GC 仅清理明确未使用且附件已经物理删除的许可；已使用/旧格式许可与 incoming/outgoing 均保留。没有给每次消息增加全 meta JSON 扫描，也没有按时间删除幂等收据。未采用“附件不在就删”的建议：共享墓碑及附件 GC 后，原请求本来仍可成功返回 duplicate；简单删除会破坏这个成功边界。回归覆盖当前与旧兼容写入器（直接发送、无二次上传初始化）、重启、个人删除、共享墓碑、物理 GC 后成功重放、内容冲突拒绝、来源隔离、引用落盘后事务失败回滚、已有引用创建新许可、旧格式与只退休未删除的保留。此项减少可回收孤儿，不代表记录总量已有硬上限。最终相关 6 文件 114 项通过；隔离 SQLite 的 EXPLAIN 验证消费更新和既有引用检查走附件索引、清理走 unused 索引及 meta 主键，未扫描全部 meta。
